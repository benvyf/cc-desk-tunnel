# 更新与发布强制规则

2026-11-05 用户明确指定。后续客户端、服务端、管理中心、宿主机 agent 及发布脚本开发均须遵守；本文件优先于历史交接中的旧更新流程。发布说明中的“历史版本行为”不能作为豁免。

## 一、服务端升级必须包含空间准备与受控断开

1. 所有升级入口必须进入统一的准备与切换流程，不能只提供一个“替换程序/执行安装”的命令。需要清理的步骤由流程默认执行，不能依赖用户手动清理或调用方记得传 `--cleanup`。
2. 构建前先做节点、签名、基线和任务状态核对，持有更新锁后回收已确认可再生成的资源：APT 下载缓存、未使用构建缓存、无容器或回退引用的旧 CC 候选镜像、无引用的旧解包文件。只回收当前安装方式实际产生的资源，不为不涉及 Docker 的普通程序升级引入全局 Docker 操作。
3. 清理前检查引用和路径归属；当前服务、所有运行/停止容器引用的镜像、必要回退资源、账号、项目与会话数据、管理员策略不得误删。不使用全局 `system prune`/`volume prune`、强制镜像删除或按时间盲删备份。保留足以溯源的失败日志。
4. 下载/解包/构建前评估空间，构建和离线预检后再次回收临时缓存、复核备份/恢复预算，冻结切换前再次确认。空间不足必须在停止原服务前报告可用量、需要量和缺口，不能跳过冷备份或降低保护阈值来“保证成功”。
5. 只有签名、环境、离线预检和空间检查通过，并确认没有运行/等待任务或占用中的原生终端，才受控断开客户端。切换期间阻止重连启动新任务；空闲客户端不要求用户逐个手动关闭。不得为了升级强杀用户正在进行的工作。
6. 冷备份、校验、切换、健康检查及失败回退属于一个有记录的流程。尽量缩短停机窗口，支持异常后判断当前阶段，不自动重放有副作用的命令。不承诺断电、硬件故障或任意磁盘容量下绝不中断。
7. 已发布脚本和安装包不可原位覆盖。改变签名包内的迁移脚本必须使用新 Build、重新签名、更新精确续期登记，并验证管理中心实际 agent/命令会选择新入口，而不只是检查本地源码。

**服务端发布门槛：** 验证默认入口不带可选清理参数仍执行空间准备；空间不足/清理失败不停止原服务；忙碌任务阻止切换；空闲连接自动断开；失败可恢复；当前/回退引用保护有效。宿主机迁移应在 Linux 隔离环境执行相关测试，模拟与实机结果分别记录。发布后核对真实签名、完整下载摘要、续期、agent 路由及未授权节点/通道保持不变。

## 二、新客户端必须保留后续更新提示和获取能力

1. 每次创建客户端，都必须保留受管更新控制器、主进程 IPC、preload、状态订阅、UI 提醒、固定发布源/公钥、安装身份、配置目录及更新账本。不得因重构、主题修改、打包裁剪或协议升级丢失其中任一环。
2. 登录前、已登录、断开服务端以及协议不匹配时，都要能独立检查客户端更新。更新检测不能依赖先成功连接 Ubuntu，不能因当前忙碌而永久隐藏新版本；忙碌可以阻止安装，但不应掩盖可用版本。
3. 检测到经签名验证且高于当前安装/确认 Build 的新版，必须显示目标版本、Build 和可操作入口。同 appVersion 的更高 Build 也要提示。保留启动自动检查、周期检查和手动重试；网络失败与“没有新版”必须区分。
4. **协议兼容只决定如何安装，不能决定是否提示。** 跨协议新版仍显示版本和配套要求，不能清空新版元数据，也不能把协议不匹配当成“已是最新版”。查看配套版本后再次检查，不得因更新账本变化把提醒误隐藏。
5. 用户必须能从客户端入口点击获取新版，不应每次手动复制 URL。相同协议使用现有下载/校验/安装流程；跨协议在提醒中提供一键打开经签名验证的完整安装包下载，并明确服务端配套与关闭窗口要求。可以要求用户确认安装，不可只留“联系管理员”而没有正常获取入口。
6. 显示或打开手动完整包不授予跨协议自动安装权限。继续检查签名、来源、Build、摘要、防回放及安装前任务/进程状态；不能伪造协议、关闭校验或发送任意 renderer URL 来绕过限制。
7. 发布新包后登记精确 expectedRelease、干净源码及独立制品路径，验证真实 systemd 续期和 timers。仅生成本地 EXE、仅改发布页面或仅更新版本号，不算更新功能发布完成。
8. 对已发行、缺少上述能力的旧客户端，不能声称服务端能远程注入本地修复。需明确一次性迁移方式；从具备修复的新包起持续验证后续链路，不能把“以后都手动下载”作为常规流程。

**客户端发布门槛：** 用真实已验签索引经过控制器生成状态并检查 UI，不只给界面 mock 一个 `available`。至少覆盖同协议更高 Build、跨协议更高 Build、登录前/断开、网络失败重试、手动查看后提醒保持、拒绝旧版/回放及跨协议自动安装。验证客户端内下载入口可用，实际打包 EXE 的身份/组件/preload/控制器完整，线上下载/hash/签名与续期一致。

## 当前基线及未完成边界

- 服务端默认清理及受控断开以 [Build 14](RELEASE-SERVER-BUILD14.md) 为当前实现基线；空间不足仍安全停止，不把“清理过了”当成一定有足够容量。
- 客户端跨协议提示修复以 [Build 29](CLIENT-BUILD29-PUBLICATION.md) 为基线。该版本修复了提示元数据丢失；协议兼容的下载和工作空间要求升级时的一键完整包入口已有实现。**独立更新弹窗的跨协议分支仍只提示配套升级，尚无直接获取完整包按钮，不得因此声称已全面满足本文件第二节第 5 条；下一次客户端功能/发行必须补齐并验收这一缺口。**
- Build 27 的旧代码需要一次性手动安装迁移，不能把本条历史例外扩展成新客户端的常规行为。
- Claude CLI、SDK、账号和模型网络始终在 Ubuntu；更新功能不能新增本机或开发目标设备代发模型请求的路径。

## 执行方式

开始相关开发或发行时先读取本文件；只修改直接相关代码，复用现有流程，不为假想故障建设新框架。修复先复现，关键路径有针对性验证，已通过且未改动的旧模块不反复全面审查。交接和发布记录必须列出实际检查、真实/模拟范围及未完成事项；未达到对应门槛不得称为发布完成。
