# 宿主机更新：默认空间准备与客户端断开

2026-11-05。用户回传 Build 12 在构建及离线预检后，仅剩 124301312 字节可用，备份/恢复要求 2726797970 字节，更新在切换前停止，原服务仍在运行。

后续 Build 13 清构建缓存后仍缺约 45.7 MiB，已按用户授权扩展 [Build 14](RELEASE-SERVER-BUILD14.md) 的有条件清理：APT 下载缓存、无容器/回退引用的旧 CC 候选镜像和旧解包 program/。下方“仅清构建缓存”为 Build 13 的原始范围，当前规则以 Build 14 说明为准；备份、策略及引用中的资源仍不自动删除。

## 根因及修改

管理中心实际使用的宿主机 agent 从签名包启动 `apply.py --release ... --install`，没有 `--cleanup`。Build 12 包中的清理依赖该参数，导致自动入口没有执行构建缓存清理。

现已将签名迁移脚本改为默认两次执行 `docker builder prune --all --force`：

1. 核对节点、签名、基线及任务空闲后，清理未使用构建缓存，并检查构建及备份预算；提前失败不停止服务。
2. 解包后再次检查预算，构建候选镜像并完成离线预检。
3. 再清一次构建缓存，重新确认冷备份和回退所需空间。
4. 沿用原有安装事务：冻结并复核没有运行/等待任务，复核空间和原配置，隔离旧容器网络并停止服务，使客户端自动断开且无法抢先重连。
5. 完成并校验冷备份，再切换候选服务；健康检查失败沿用原有回退。

保留 `--cleanup` 参数供旧调用方使用，但不再决定是否清理。用户无需先手动关闭所有空闲客户端，也无需手动添加清理参数。运行中的任务仍阻止升级，不强制终止工作。

只清理未使用 Docker 构建缓存，不运行 `docker system prune`、`image prune` 或 `volume prune`，不删除原镜像、容器、项目数据、账号、管理员策略及冷备份。清理失败立即停止；清理后空间仍不足同样在断开客户端之前停止，不能以跳过备份换取继续安装。突发断电、硬件故障或系统强杀无法绝对保证不中断；保留原有恢复记录和回退机制。

## 当前验证与上线边界

新增默认清理、清理失败、空间不足继续阻止切换、清理范围测试；迁移入口测试增加无 `--cleanup` 时构建前/预检后各清理一次，以及构建后低空间不调用安装。已有安装事务的空闲断开与回退路径保留。

本地 Windows 可运行的测试通过；依赖 Linux `fcntl`、根目录权限和容器的测试按平台跳过，不能将其计作 Linux 实机通过。未访问或清理生产 Ubuntu 的磁盘，未触发任何更新任务。

用户已授权上线，修复按 [Linux Build 13](RELEASE-SERVER-BUILD13.md) 新签名发行。已发布 Build 12 的迁移脚本在签名归档内，不能直接覆盖旧包或原摘要；必须选择新的 Build 13 更新任务，不能重试旧 Build 12 任务并宣称默认清理已生效。

对于当前已出现空间不足的节点，可由用户先执行 `sudo docker builder prune --all --force` 清理相同范围的缓存，然后检查 `df -h /var/lib/cc-runtime-upgrade`。空间仍不足就保留原服务，不反复触发构建，也不删除回退资源；需先定位占用并扩容或另行确认清理范围。
