# SSH 输入竞态修复与验收

2026-11-04（香港时间）。本次修复基于 `18715311ccb5f6fa1b3bb62947f9ae15b67852cc`，保留现有模型调用链路与协议 24。

## 问题与修复

OpenSSH 可以在收到执行确认前发送脚本及 EOF，也可以提前发送 SFTP INIT。原适配器等待目标端确认后才接受本地请求；此时 ssh2 尚未创建可接收输入的通道，数据被丢弃，提前 EOF 还可能使稍后的接受操作失败。实际表现是开发通道探测或原生 scp 挂住。

现在先接受本地 exec/SFTP 通道，由 SSH 接收窗口和流缓冲保存输入，再等待目标端确认并衔接两端。目标打开失败时，exec 以 255 结束，SFTP 通道关闭；失败不影响同一适配器上的后续请求。

提前接受还需要处理取消：ssh2 可能已经把 SSH 通道标记为关闭，却没有设置 Node 流的 `destroyed`。迟到的目标端回调如果只检查 `destroyed`，仍会将缓存输入发给目标。现在衔接前同时检查输入端是否完整关闭、输出端是否仍开放，关闭后销毁迟到通道。输入 EOF 仍是正常的脚本完成标记，不会被当作取消。

## 回归测试

测试使用两段真实 SSH 握手和受控目标，确定性覆盖：

- 目标延迟确认时，提前发送的脚本/EOF 与 SFTP INIT 都完整保留。
- 调用方在确认前关闭时，缓存脚本和 SFTP INIT 都不会在迟到回调后被转发。
- exec/SFTP 打开失败及关闭后的错误回调正确收尾，适配器仍能处理后续请求。
- 原有主机指纹、加密私钥、输入输出、退出码、大输出、SFTP 文件和设备隔离回归继续通过。

关闭回归使用同一目标 SSH 连接上的后续通道作为传输屏障，避免通过固定等待时间猜测数据是否到达。原始输入丢失行为及 review 中的关闭竞态均先复现失败，再验证修复通过。

本机便携式虚拟机运行两套独立 Alpine Linux 3.24.3，内核 6.18.58-0-virt，使用 OpenSSH 10.3p1、Bash、GCC 15.2.0 和 Node 24.22.1。服务端在 Linux A，桌面 SSH 管理器和适配器在 Windows，项目操作指向 Linux B。

12 项验收通过：环境和服务启动、两台目标接入、指纹与密码认证、中文/空格目录浏览、读写搜索及 C 编译、原生 scp 二进制往返与摘要一致、3 MiB 输出及退出码、手动重连恢复已有会话、不重放命令、取消、目标 SSH 进程故障恢复，以及受控模型请求来自 Linux 的验证。

两台设备拥有独立文件系统及同名项目，目标 B 的开发操作没有修改 Linux A 的同路径项目。虚拟机不挂载用户目录，使用临时测试身份；实验结束后相关进程和监听端口已清理。

测试工具另有 11 项失败路径检查，覆盖中断、超时、端口占用、清理失败、并发校验与旧证据混入。报告仅在同轮运行编号、源码摘要、实际 TAP 日志、回归和补丁证据匹配后生成；测试工具与临时环境保留在本机验收目录。
