# JEV 重复消耗修复方案

日期：2026-10-24。以下是完整设计，不代表全部实施。用户随后限定先做小范围两项：跨入口精确内容缓存，以及问答重复拼接修复。缓存改动可独立部署控制中心；hook修复受镜像保护，只交付已测试源码，待管理员镜像维护。持久化、工具错误来源区分和费用界面不在本轮范围。当前状态以[审核说明](MODERATION-NODE-GATE.md)与交接为准。本次未调用真实 Claude/JEV，未读取生产消息正文或账号凭据。

## 目标与约束

同一节点、同一会话、同一策略和完整待审上下文下，复用已取得的审核决定；并发检查、不同界面入口、工具循环和控制中心重启不应各自重复付费。新增用户信息或审核策略变化必须重新判断。

保留现有执行前检查点，只合并付费决策。官方 CLI 二进制、SDK 调用、登录、Claude 请求及回复、权限流程、遥测和原生上下文压缩不因本次修复而改变。审核成功仍只返回空 hook 结果，不往 Claude 上下文注入审核说明、审核凭证、摘要或纠错提示。审核组件不另行请求 Claude。

不得将“一条输入审核通过”替代“包含这条输入的另一份历史审核通过”。不得通过关闭 hook、扩大权限或截断待审历史达到省费目标。

## 已确认的消耗来源

离线调用当前文本构造与 NodeReviews，审核提供方使用内存假实现：

| 场景 | 当前审核调用次数 | 问题 |
| --- | ---: | --- |
| 首条相同输入分别经过聊天层与原生 hook | 2 | 缓存仅覆盖 native-terminal，且后续轮次两层使用不同文本 |
| 一个问题后执行八批普通成功工具 | 1 | 上一轮缓存已解决这一类重复 |
| 一个问题后出现两个工具错误，无新用户文字 | 3 | 所有 is_error 工具内容被纳入待审历史 |
| 同批两个问答结果，再执行普通工具 | 2 | transcript 与 tool_calls 重复拼接，随后文本恢复原状又重新审核 |

生产脱敏记录核算曾发现最近24小时15条相同已通过原生文本的再次审核，合计报告121,591 Token。该窗口包含上一轮修复前记录，不能将这一比例当作修复后或未来的节省承诺。此前离线复现脚本位于忽略目录 .local/analyze-jev-consumption.mjs。

## 一、统一审核对象，保留原始用户文字

聊天预审和原生 hook 共同使用一套文本提取规则。输入由有序用户消息、问答及其问题、权限反馈和本次自定义压缩要求组成；保留各项边界和顺序。

- 用户消息采用原始文字，不根据敏感词、否定或可疑段落进行删改。
- 同一个工具结果按稳定的 tool_use_id 只提取一次；同批 tool_calls 用于核对 transcript 是否已完整落盘，不再次附加相同结果。
- 同内容但属于两条不同用户消息时，保留两条。不能用全局字符串去重删除真实的新输入。
- 聊天预审应基于官方会话读取能力和本次待发输入构造完整审核对象，不再只审单句；hook 使用实际收到的会话内容再次核对。
- 本地系统生成的封装与真实用户文字只按可信来源区分，不能仅凭相似前缀、标签或字符串格式删除用户文本。
- SDK 问答 JSON 与原生工具结果的等价转换必须由固定版本离线样本验证；不可证明等价时保留复审。
- 会话运行中的排队输入、分叉、恢复和压缩需要核对实际上下文。不能只凭 sessionId 或 prompt_id 相同直接放行。

完整审核对象相同时，两个入口共享同一结果；hook 发现预审未包含新文字、权限反馈或其他差异时才产生新审核。不得把仅有局部文本的旧通过结果扩展为对更大文本的授权。

## 二、控制中心保存审核凭证与调用状态

复用键包含节点、会话、配置 revision、规则版本、文本构造版本和完整审核对象摘要。界面 deviceId、hook 类型和随机 requestId 不作为相同内容之间的隔离条件；它们继续保留为溯源元数据。节点/会话之间不共享决定。

在现有控制中心 SQLite 中保存摘要、决定、审核编号、有效期与调用状态，不保存原始文本。复用范围有明确保留期，配置或文本构造规则变化后失效。已有历史记录只有在能确认版本和完整文本一致时才可作为通过凭证，不批量将历史局部审核迁移为新通过凭证。

- 同时到达的相同请求共用一项进行中的审核。
- 成功结果持久化后才能作为可恢复的通过凭证，服务重启不清空有效凭证。
- 拒绝可以复用为拒绝，不能作为通过；人工重新评估应明确属于新的付费动作。
- 请求 ID 的内容冲突仍须拒绝，不能因内容缓存而绕过。
- 缓存检查不应先消耗每个随机 hook 请求的付费审核容量；容量保护针对真正的新审核和必要的请求处理。

服务商调用与本地数据库不是同一事务。调用前持久记录进行中状态；超时、断线或进程中断后，服务商可能已经处理并计费。若服务商没有经确认的幂等接口或结果查询能力，不能承诺端到端严格只扣费一次。此时保留“结果未知”，不自动重发、不假装通过，由管理员明确重试。不能把每次新的随机 requestId 当作重新付费的理由。

凭证到期、策略改变、上下文不能确认或未知调用后的明确重试，均可能需要新审核，必须在界面说明原因。

## 三、区分工具错误和用户权限反馈

当前不能直接排除全部 is_error 结果：用户在权限弹窗填写的拒绝原因也可能进入错误结果。

官方 PostToolUseFailure 在已经开始执行的工具失败时触发；权限拒绝不触发该事件。方案是在确认固定 CLI 版本实际支持该行为后，用轻量 command hook 记录节点、会话、tool_use_id 与错误内容摘要，作为机器执行失败的来源证据，不调用 JEV、不注入 additionalContext、不改变权限决定或工具返回。

PostToolBatch 仅在工具 ID 与实际错误内容均能和执行失败证据对应时，排除该机器错误。找不到证据、内容不一致、事件缺失或混合用户文字时仍保持保守审核。证据的注册、读取与顺序关系必须离线验证，不能仅按 Exit code、Error 等字符串猜测来源，也不能依靠未经核验的工作区可写放行文件。

PermissionDenied 不适合作为手工权限反馈的替代：官方文档明确它只覆盖 auto 模式拒绝，不覆盖用户手动拒绝。

问答、用户拒绝理由、Tab 补充要求和自定义压缩要求继续作为新增用户信息审核。普通工具执行及能确证来源的机器报错不因自身变化额外付费。

## 四、保留必要的多轮上下文

当前 JEV 调用由每次请求提供 state 与 questions；现有集成没有跨请求保存会话上下文的服务商能力。用户各句分别通过不代表组合用途通过。

第一阶段继续携带判断新输入所需的完整用户上下文，优先消除双入口、重复拼接、相同工具循环、可确认机器错误与重启遗忘造成的消耗。不得为省 Token 改写 Claude 历史、强制原生压缩、请求 Claude 生成审核摘要或静默丢弃旧用户输入。长会话的上下文成本与输入上限仍是这一阶段保留的限制，不能宣传为已经消除。

只有服务商正式支持并验证上下文/前缀复用，或另行验证具有明确准确性取舍的增量审核策略后，才进一步减少每次提交的历史长度；需要单独说明判断能力的变化。

## 五、让费用可追溯

控制中心将“检查次数”“凭证复用次数”“实际 JEV 尝试次数”“服务商报告 Token”和“结果未知”区分展示。缓存命中不伪造新的 JEV 调用和费用；工具循环使用汇总计数，避免每次复用都新增完整审核记录。

每次真正调用注明原因：首次审核、新用户输入、新问答/反馈、策略变化、凭证过期、上下文差异或管理员明确重试。没有 usage 的请求显示未知，不能据此标为免费。

## 验收与发布

只增加与上述改动直接有关的核心离线回归，提供方全部使用模拟实现：

1. 同一完整审核对象依次和并发经过聊天预审、原生输入、工具批次，只产生一次实际审核调用。
2. 同批多个问答、重复 hook、连续相同文字的新用户消息不会因错误拼接丢失信息或产生假变化。
3. 普通成功工具、具有匹配证据的工具执行失败不新增调用；无证据的失败、用户权限反馈不被错误跳过。
4. 控制中心重启仍复用有效已完成结果；规则、策略、节点、会话、上下文或有效期变化按边界重新审核。
5. 模拟服务商已经处理后本地断线/崩溃，不自动启动第二次付费请求，也不放行未知结果。
6. 排队输入、恢复、分叉、压缩、No/Tab 反馈仍在到达模型前完成必要审核。新增官方 hook 能力需在无网络、无账号的固定版本隔离环境验收。
7. 对 Claude 的输入字节、官方二进制/SDK、登录、环境、权限设置和模型请求次数没有因审核优化改变；成功 hook 不向模型加入审核文字。
8. 生产验证只做版本、签名、配置、就绪和元数据检查；由正常使用观察用量，不发送真实 Claude/JEV 验收消息。

先实现控制中心持久幂等与费用溯源，再通过正式服务端升级统一文本提取和来源判断。新旧节点按文本构造版本区分，旧节点不会自动获得不适用的凭证。发布仍使用现有签名与回退流程，不通过在线修改官方 CLI 或远程补丁跳过发布校验。
