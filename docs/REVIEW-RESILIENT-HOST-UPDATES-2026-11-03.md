# 更新流程第二轮细节复查

2026-11-03，香港时间。审查基线为 c3b4727，范围为用户批准方案对应的更新、接入、维护准入、备份、恢复和发布包。本轮不发布 VPS，也不替换 Ubuntu 业务服务。

## 发现与修正

| 细节遗漏 | 影响 | 已落实的修正与验证 |
| --- | --- | --- |
| 接入时先移走旧目录，再放入新目录 | 两次操作之间遭遇强制退出，systemd 指向的 agent.py 可能不存在 | 改用 Linux renameat2 原子目录交换；先探测支持能力，再消耗接入码；同步文件及目录元数据。Linux 子进程实际交换后 os._exit(77)，正式路径和备用路径均保留完整程序 |
| 自动断连接口只检查原始 socket 地址 | 本机反向代理可能把远端请求呈现为回环连接 | 同时核对实际来源地址；实际 HTTP 请求验证代理转入的远端来源被拒绝，未进入准备阶段 |
| 普通安装和宿主机安装缺少共同的准备所有权 | 并发入口可能交错维护和准备状态 | 业务子进程内使用共同的安装准备锁；一个请求准备期间，另一个得到 409，不能进入维护或重复准备 |
| 配置及策略复核发生在冷备份之后 | 准备期间有管理员修改，可能先停服才发现变化 | 冻结后、断网与停服前检查容器快照及策略摘要；原切换创建处保留再次检查。回归验证异常路径没有断网或停服 |
| 暂停请求结果不确定时，记录仍是 prepared | 下一次更新可能掩盖暂停状态并在 docker exec 处等待 | 暂停前持久记录 admission；只有确认解除暂停后才恢复 prepared。结果不明时拒绝新更新并指向既有恢复目录 |
| 备份与回退脚本只关闭文件，未显式同步落盘 | 掉电时可能恢复记录已持久化，而归档或离线脚本字节尚未持久化 | 暂停前同步备份目录和离线脚本；冷备份验收前同步归档字节。注入同步失败，验证不接受该备份 |

同时补齐两项恢复细节：接入响应丢失不再与明确拒绝混为一谈；目录交换成功后先设置已交换标记，再同步元数据，确保同步异常仍会交换回旧程序。

- Linux Python：27 个原升级用例、16 个新升级用例、6 个 agent 用例、7 个接入用例，共 56 个通过，无跳过。
- TypeScript 全项目检查、Git diff 空白检查通过。
- 发布包重新生成后核对全部运行文件摘要、独立导入运行时、生成接入安装器的内容与语法。
- 原子交换强制退出、并发接入锁均在 Linux 实际运行；Docker 和业务升级仍由模拟引擎测试，不调用 Claude。

## 保留的上线条件

没有把代码测试当作所有节点已采用。VPS 中心发布、Ubuntu 重新接入、携带新 supervisor 的签名服务端发布、首台设备真实升级验收仍属于上线步骤。旧 supervisor 不具备新普通自动断连能力时保留严格安装入口，不绕过准入。

接入响应在网络中丢失，或磁盘实际不足，仍可能需要人工处理；这些路径必须报告真实结果并保留现场，不能承诺任何环境下永不中断。
