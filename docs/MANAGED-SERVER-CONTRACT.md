# Managed Linux program updates, version 1

This contract is separate from the Windows update contract and the business WebSocket protocol. The immutable image starts `managed-main.ts`, which enforces the administrator's read-only native policy before starting the supervisor. The supervisor forks the selected program as container UID 1000, preserving the initial effective environment, data directory, TLS configuration and working directory. It never installs dependencies or invokes Claude for checks.

The image trust identity is `deploy/managed-server.json`: product `cc-desk-tunnel-managed-server`, channel `pilot`, origin `https://api.ghostapi.org`, baseline build 1. The index is `/cc-updates/server/v1/channels/pilot/linux-x64.json`. Artifacts use `/cc-updates/server/v1/artifacts/{build}/linux-x64/cc-desk-tunnel-server-{appVersion}-build{build}.tar.gz`. Neither clients nor journal files can supply another URL or executable path.

`packages/managed-server/src/index.ts` exports the authoritative TypeScript types, `signServerIndex`, `verifyServerIndex`, `buildDescriptor`, `compatibility`, `releaseFilename`, and hashing/size constants. `buildDescriptor(staging, {build, appVersion, protocol, sourceCommit})` inventories the complete staging directory except `SERVER-RELEASE.json` itself. Write the resulting JSON as `SERVER-RELEASE.json`; the signed release's `descriptorSha256` hashes those exact serialized bytes. Whitespace in the descriptor is permitted.

The signed envelope has exactly `payload`, `keyId`, `signature`. Payload and Ed25519 signature use canonical unpadded base64url. The signature covers the decoded UTF-8 payload bytes. The payload has exactly `schema:1`, `product`, `channel`, `platform:'linux'`, `arch:'x64'`, `revision`, `issuedAt`, `expiresAt`, `release`. Times use ISO UTC with milliseconds; the validity interval is at most 31 days. The release has exactly `build`, `appVersion`, `protocol`, `sourceCommit`, `size`, `sha256`, `packageLockSha256`, `runtimeLevel`, `compatibility`, `descriptorSha256`. Source commits are 40 lowercase hex characters; SHA-256 fields are 64 lowercase hex characters. Revision/build floors survive restarts; changing an artifact under an existing build is rejected. Expired indexes block new installs, while previously verified installed releases can restart or roll back offline.

The descriptor has exactly `schema:1`, `product`, `build`, `appVersion`, `protocol`, `sourceCommit`, `files`. Each `files` entry maps a relative archive path to `{size,sha256}`. The gzip archive must contain only regular USTAR file entries, including the descriptor and exactly its inventory. Directory entries, links, PAX/GNU extensions, duplicate paths, traversal, node_modules and unlisted files are rejected. Limits are 64 MiB compressed, 256 MiB expanded, 10,000 inventory files, 4 MiB descriptor, and 128 KiB signed index.

Only runtime level `node24-cli2.1.295-v1` can install into this image; this maps to Node 24, immutable `/opt/runtime/level` text `1`, and the existing administrator-owned CLI. A release must match the image's exact lockfile digest and every exported `COMPATIBILITY_PATHS` digest. Those paths cover SQLite persistence, native settings/onboarding/instructions, and the complete immutable moderation hook closure and native policy enforcement. Changed runtime, dependencies, persistence or policy require an administrator image upgrade. The immutable loader resolves the candidate's protocol workspace while retaining the image's installed third-party dependencies.

`compatibility(root)` also pins the persisted protocol schema closure and certificate/TOTP/home-state serializers. For `packages/protocol/src/index.ts` only, it normalizes the numeric literal in the single exact standalone `export const PROTOCOL_VERSION = digits;` declaration to zero before hashing. Every other byte, including protocol history, schemas and helpers, is pinned. Thus a handshake number change can use a program update; a schema/history change conservatively requires an image upgrade. Descriptor file hashes always cover raw file bytes. Installation compares the signed compatibility map to `compatibility(stagedRoot)`, never substitutes raw descriptor hashes for normalized schema hashes.

All management requests use `Authorization: Bearer <existing service token>` (at least 24 characters). Any Origin header is rejected; authentication failures and concurrent pending requests are throttled. POST bodies require `Content-Type: application/json`, a 4 KiB limit, exact fields and positive integer protocol/build values. Management endpoints remain reachable during maintenance:

- `POST /cc-managed/server/v1/check`: `{clientProtocol}`. Returns `ServerCheck`: signed `index`, `candidate`, `current`, `compatible`, `reason`, and `schema:1`. Reason is `available`, `current`, `protocol-unavailable`, `manual-image-upgrade`, `disabled`, or `busy`. Clients should independently verify the returned envelope before displaying an exact build/hash confirmation.
- `POST /cc-managed/server/v1/install`: `{clientProtocol,confirmed:true,build,sha256}`. No automatic installation occurs. Busy service or changed/incompatible release returns 409. Once staging and revalidation succeed, returns 202 `{accepted:true,build,sha256}` and activates the upgrade after the response flushes (or the client disconnects).
- `GET /cc-managed/server/v1/status`: `ServerStatus`, including `schema:1`, `phase`, `current`, `target`, and an optional bounded error code. Current program is `{build,protocol,appVersion,sha256}`; the immutable baseline's archive hash is null.

Maintenance admission synchronously closes HTTP mutations and all WebSocket admission before checking runs, terminals, login, mutations, review work, input queues, tracked tasks/tunnels, pending Web HTTP and authenticated/registering peers. The supervisor durably journals staging, stop, cold backup, switch, probe and commit. It confirms both private IPC and authenticated loopback HTTP readiness using a random launch nonce, expected build/protocol/release/policy hashes and a real opened-store query. The candidate remains in maintenance until commit. `/health` alone never authorizes commit.

Preparation has a 120-second overall deadline, shorter than the 180-second child IPC timeout. The preparing child must remain alive. After preparation succeeds, activation must arrive within a 10-second handoff lease; failure, timeout or owner exit cancels the prepared target and releases maintenance. Preparation checks the wall-clock deadline after synchronous staging work as well as aborting pending downloads.

Before backing up, the old child and its process group must exit. Backups retain configuration, service state, native home state and the effective `CLAUDE_CONFIG_DIR`, including an external configuration directory. Ancestor backup roots are deduplicated, filesystem roots and sources inside managed state are rejected, and copying a data ancestor explicitly excludes the managed-state subtree. The backup manifest records its source roots. Crash recovery and failed readiness switch only program pointers; candidate-written data is retained and never overwritten by a backup. Active and previous installed inventories/signatures are reverified at every startup. Unhealthy installed candidates fall back to the verified previous program.

Production requires a Docker restart policy. An unexpected committed business-child exit stops its known process group and exits the whole container, so separately grouped native PTYs cannot survive into a replacement server. A durable journal counter limits unexpected exits and failed startup readiness to three across container restarts; reaching the limit prevents another business-child launch until administrator intervention. The supervisor's injected non-production harness can instead exercise finite in-process recovery. Container shutdown disables relaunch. Legacy downloaded-program pointers and the GitHub updater remain unused. Source builds without a release descriptor continue running with management checks reporting `disabled` until an administrator installs a prepared image.
