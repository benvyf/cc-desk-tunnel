目标是吸收上游对现有内嵌终端和设备执行有实际收益的部分，保持 CC Space 的多标签终端、独立官方历史、跨设备协作和 SSH 远程开发。

## 3. 第一批：路径与上下文统计

### 3.1 Windows 文件传输路径

修改 `apps/server/src/device-terms.ts` 中 Windows 的 scp/sftp 描述：盘符路径统一写成 `device:/C:/目录`，不能只把反斜杠替换为正斜杠。

- 只对 `^[A-Za-z]:` 形式增加前导 `/`；POSIX 和已规范的路径不重复加斜杠。
- 保留项目路径原值，只改变传输示例，不能修改 `pathKey`、项目身份或数据库路径。
- 空格、中文、引号按具体 shell/参数正确引用；不把 JSON 展示转义当成 shell 转义。
- UNC 不假定与盘符相同。实施时使用现有支持范围；若没有已验证表示，则不给出伪造的盘符示例，并明确尚未验证，不扩建网络盘支持。
- `remotePrompt()` 中的新描述影响新生成提示词；既有会话不会自动读到。利用现有 `store.notice()` 增加一次性设备说明修订标记，在下一条正常消息补充路径规则，不重写旧记录、不自动发模型请求。标记随现有 `prompt/told` 元数据保存，默认值代表未通知；覆盖既有会话、后续新会话不重复通知。
- 标记使用递增的说明版本，路径修正与后续 Shell 变更分别推进版本，不能共用一个布尔值导致第二次变更不再通知。复用现有元数据，不新建通用通知系统。
- `store.notice()` 当前只在聊天 SDK 的提交路径被调用，且调用时即保存 `told`，并非模型已收到的回执。本批不承诺严格一次送达；验证消息被拒绝/未送达后的重试沿用现有输入去重机制，必要修正限于新增说明。不能在渲染器或 PTY 原始按键里偷偷插入提示词。
- 已经打开的内嵌 CLI 不会收到该聊天通知。路径说明随下次用户主动关闭并重新打开终端时的新提示生效；不为此强制重启、自动发消息或运行 `/compact`。

修改点：`device-terms.ts`、`claude.ts`、`store.ts`，以及保存提示元数据所需的 `packages/protocol/src/index.ts`。现有 schema 解析后仍需保留标记，不能只写入会被解析剥离的临时字段。

`promptValues()` 仅固定项目和平台，并未保存完整旧提示词模板。更改 `remotePrompt()` 的静态文本后，后续新 SDK/CLI 进程可能一次性失去旧提示缓存；“用 notice 通知”并不能消除这个变化。本方案接受并明确说明这项一次性影响，不为避免它复制长期维护的旧模板，也不承诺零额外 token。后续仅切换 Shell 偏好/能力时保持模板文本和已保存初始描述稳定，由消息通知更新，避免每次切换都改变系统提示词。

### 3.2 终端上下文统计

在 `terminal-transcript.ts` 增加纯转换函数，读取 CLI 状态栏中的 `context_window.current_usage`：

```text
used = input_tokens + cache_creation_input_tokens + cache_read_input_tokens
window = min(模型窗口, 本次 CLI 实际生效的 autoCompactWindow)
percentage = round(used / window * 100)
```

没有有效自定义窗口时使用模型窗口。缺少有效用量时返回未知，不发布“0%”，不伪造分类或新增费用统计。

与上游不同，本项目不能直接全局调用 `readNativeSettings()`：当前 PTY 可以使用不同 `CLAUDE_CONFIG_DIR`，且有 provider `--settings`、临时 settings 和项目配置。实施时以当前 `continued.config`、实际 cwd、本次生成的 settings 为依据，按所用 CLI 版本核对设置优先级；优先复用已有配置读取能力。不能仅凭配置文件名称声称取得了有效值。若无法确认覆盖后的窗口，显示状态栏模型窗口并注明口径，不能默默套用另一目录的设置。

本批应通过 CLI 的实际行为固定设置优先级和生效时点。运行中的进程未采纳配置变化时，统计不能提前使用新设置；新 PTY 才使用新快照。`/model` 引起模型窗口变化则以新状态栏数据更新。

调整 `server.ts` 的 `terminalQuota()`：分别判断上下文和额度变化，不能因为 `windows` 为空或额度没有变化就丢弃上下文更新。复用 `native.metrics`，保留已有 `usage` 和额度口径；不把每秒读文件都记成一条新事件，只在有效内容变化时发布。结束时核对最后状态，不添加缓存 TTL 或缓存计时。

去重比较只包含模型、token 数和窗口等有效值，排除每次转换新生成的 `measuredAt`。上下文刷新按会话订阅发布；只有账号额度变化才沿用账号范围广播。没有额度的上下文事件不能把 `Quotas`、账号监控的有效额度或新鲜度改成空值。CLI 状态文件缺失/损坏时保留最后有效值及其测量时间，不能伪装成刚测得的新值。

验证：盘符路径与实际 SFTP 上传/下载；上下文原始窗口、较小/较大自定义窗口、配置目录隔离、无额度但上下文变化、用户原状态栏仍运行。实际传输和 CLI 口径验收在隔离环境完成，不在生产项目试写。

## 4. 第二批：增量同步、迟到回答和命令展示

### 4.1 读取器：沿用受控历史身份

在 `terminal-history.ts` 内增加增量入口，复用 `openTerminalHistory` 的路径和文件约束，不直接复制上游 `terminalRecord(path, offset)` 的裸路径读取。

初始全量历史与 `known` 仍由现有真实 SDK 读取建立。增加每个终端实例的文件游标和长期存活的转译器；状态挂在现有 `continued` 下，不建立全局状态库或额外持久任务。

- 路径由 `(continued.config, 实际 cwd, continued.nativeId)` 推导。hook 只需生命周期字段；若确实需要 `transcript_path`，它只能用于核对预期路径，不作为可直接打开的任意文件入口。保留当前瘦 hook，不重新保存提示词和工具输出。
- 初始快照与读取起点必须来自同一个已校验文件快照：先在同一文件句柄捕获边界，再只解析该边界内的完整记录并交给 SDK。不能先 `readTerminalMessages()`、后单独 stat 取新 size，两步之间新增的记录会被直接漏掉。路径替换时重新核对，不用文件 mtime 代替快照边界。
- 按字节偏移读取新增完整行；最后一个未结束的 JSONL 行保留到下一次，不将 UTF-8 多字节字符切坏，不在每次轮询重新读取整份历史。
- 追加路径只接受所绑定 nativeId 的主会话数据。SDK 的 `getSessionMessages()` 还会按 `parentUuid` 选择会话链，不能把过滤 `isSidechain` 等同于 SDK。保留当前有效链端点，只有能确认延续当前链的记录才立即发布；分支/回退或父链无法确认时走 SDK 全量核对，不先发布可能被撤销的分支。压缩摘要/边界的识别先于一般 meta 过滤，避免丢掉 `/compact` 标记；压缩边界与摘要跨批次时保留待关联元数据。
- 文件缩短或被替换时使当前游标失效，走受控全量核对和 UUID 去重，不能把新文件末尾直接作为“已读”。同尺寸替换不能仅靠 size 判断；利用读取器已有文件状态与轮次结束核对处理，不新增全局文件监控系统。
- 新增单次读取预算，避免轮询一次分配整个大文件；预算值按现有历史读写规模确定，完整大行分段累积，不以截断正文方式“成功导入”。
- 完整坏行保留路径、行号或字节位置诊断，不像上游一样静默跳过。该实例暂停增量导入、保留文件与游标，现有轮次结束读取继续提供可定位错误；不将失败认定为空历史。
- 区分活跃文件的完整前缀读取与退出后的最终读取：Stop 时文件仍可能有半行，不能交给当前严格全量读取器后误报永久损坏。活跃核对只将已捕获的完整前缀交 SDK；退出后的末行若无换行但 JSON 完整则允许导入，只有确实解析不完整才报告未完成。最终严格读取仍保护坏文件，不取消校验。

### 4.2 转译器：同一回答跨批次保持同一身份

将 `terminalEvents()` 的主要逻辑提取为每实例一个的 `TerminalTranscript`，保留兼容的一次性入口供全量读取及既有测试使用。

- 同一 CLI assistant ID 的多个内容块，即使分散到多次读取，也沿用同一个代理 `messageId`；工具 ID 与结果关联复用现有 `ClaudeStream`。
- 增量、Stop 全量核对和退出全量核对共用 `known` 与转译状态，不另建第二条直接向 UI 推数据的通道。
- 现有 `store.append()` 每事件自行 `BEGIN/COMMIT`，`record()` 还在写库前更新账号监控；不能直接在它外面套事务。本批为终端导入增加窄的“单条源记录 → 多个事件”原子写入入口：先收集一条源记录产生的事件，再在一个事务中分配 sequence、写 events 和会话状态，提交后才广播/更新相关观察者，成功后才推进该条的 `known` 和游标。复用现有 append 的内部写入逻辑，其他聊天写入不改为新框架。
- 事务失败则回滚并丢弃该实例当前转译状态，停止该实例后续增量与结束时自动重放，保留原历史；不能只暂停 watcher 后又在 Stop 走同一批重试。记录 sessionId、terminalId、nativeId、源位置和错误，界面显示“终端记录同步失败，原始历史已保留”；屏幕输入输出和实际任务继续走现有通道。数据库不可写时用现有非持久错误通知及服务日志报告，不反复写相同失败事件。后续恢复要核对已提交事件和原历史，不承诺关闭再打开能自动补齐此前缺失记录。
- 此原子范围只解决单条记录转换的半写入，不新增消息队列或全局恰好一次承诺。进程在提交后、推进内存前退出，客户端仍可从已提交历史重读；恢复逻辑不得把屏幕快照当成事件去重依据。
- 时间继续使用 CLI 记录时间，并沿用当前非倒退/不晚于接收时刻的约束；hook 的到达时间不替代整轮内容的原时间。
- `/clear`、`/resume` 报告了另一个 nativeId 后，沿用当前 `elsewhere` 提示，不把另一段历史串入原会话，不自动切换历史绑定。
- 标记 `elsewhere` 后停用新对话的状态栏上下文采样，避免正文未串会话、上下文百分比却来自另一个会话；原绑定文件已有迟到记录仍可在归属校验通过后读入。
- 只有绑定同业务会话、全量读取成功且符合现有条件时才发布可恢复聊天的 `native.context`。增量看到一段回答不等于可把独立官方历史并入聊天。

### 4.3 生命周期：Stop 不是最后一次磁盘写入

保留现有 `continued.heard` 串行链，将 JSONL 读取也排入同一链。优先沿用每实例约 1 秒的文件变化检测；多个变化合并为待处理读取，不重复堆积相同工作。

```text
CLI 写 JSONL → 受控增量读取 → 同一转译器 → 现有 record/store/broadcast
CLI Stop    → 完整前缀核对 → 发布 idle，但文件跟踪继续
迟到正文    → 原回答追加 → 已结束轮次更新最终回答
进程退出    → 停止新增调度 → 串行排空 → 最终核对 → 清理 → terminal.closed
```

不能把 Stop 当成解绑文件跟踪的时机。CLI 仍运行时，晚于 Stop 写入的答案必须补上。实际进程退出后进行最终完整读取；遇到完整坏行或未完成尾行报告同步未完成并保留历史，不伪造空历史或“已全部同步”。不承诺捕获进程退出后未知第三方继续写入的所有内容。

统一释放 JSONL watcher、hook/status watcher 和新增待处理状态，覆盖正常关闭、启动失败、异常退出和服务端关闭。客户端短暂断开或标签隐藏时，若既有 PTY 仍存活则继续同步；不因 UI 不可见结束 CLI。

退出路径用 `try/finally` 保证物理资源释放和终端实例注销，历史读取、事件提交或关闭通知失败不能跳过清理、永久留下会话占用；写库失败仍保留可定位日志，不伪造持久化成功。排空任务不得在同一 `heard` 链内部等待排在自己后面的任务，避免自等待死锁；进入退出阶段先禁止新的调度，再从链外等待已有任务。开始/完成读取时核对仍是当前 terminalId，旧实例的迟到回调不得影响新实例。

`run.status` 的 idle/working 表示 CLI 状态，不用正文到达推测审批或强行切换 working；保留主分支 SessionStart 的首次状态修复和快速完成时 Stop 的发布逻辑。

### 4.4 命令与轮次展示

在服务端转译阶段区分用户提示、CLI 本地命令输出与压缩边界，客户端继续使用 `message.user`、`native.notice`、`native.compact` 等已有事件。

- `/model` 这类本地命令的输出显示为说明，不冒充模型回答；清理 ANSI 色码，保留有意义的内容，长输出自然换行，不强行改写为单行或解释成 Markdown 指令。
- `/compact` 保留真实用户提问和一个压缩标记；压缩后保留片段、重复 `/compact` 和 “Compacted …” 不重复生成回答。
- `/exit`、`/quit` 不增加无意义问答，退出反馈沿用已有终端状态。
- 不能对所有斜杠命令直接过滤：自定义命令可能真正请求模型，必须保留其提问和回答。
- 本地命令与输出可能跨读取批次，不能在每次 Stop 都抢先将待判定命令固化为提问；等实际记录确定，最终退出仍无法判定时保留原始用户提问。用本地命令迟写输出用例确定 settle 时机。
- `transcript.ts` 只吸收终端轮次独立折叠、说明不延长轮次耗时、迟到回答仍归原轮的必要差异。保留既有 `turn.stats` 合并、继续按钮、分页与侧聊处理。
- 仅保存 assistant ID 不足以覆盖“下一条提问已导入，上一轮最终回答才第一次出现”。先用第 9 节真实样本确认该顺序及当前稳定 messageId 的处理结果；仅在复现不能正确归属时，为终端事件增加可选 `terminalTurnId`（原始人工提问 UUID），由源记录父链确定归属，同一源记录生成的事件继承同一键；在 `SessionEvent`、终端原子追加入口、`transcript.ts` 与 `conversation()` 中贯通。聊天事件不带该字段，旧记录沿用当前逻辑。若现有身份已足够，则不增加该字段；不能通过回拨 sequence 或伪造时间解决归属。
- hook 的 idle 只能关闭已识别的对应轮，不能把批内最后一条提问无条件视为已结束。先以真实记录验证 Stop 与下一次 UserPromptSubmit 的关联；无法唯一归属的状态只更新 CLI 活动，不提前完成某轮。分页缺少原提问时允许显示当前片段，但不能创建第二份原提问；重新加载、导出和侧聊截取沿用同一归属规则。
- 不靠读取器每批次生成新身份重建 DOM；沿用既有回答区、过程折叠、复制/导出、滚动跟随和阅读位置保护。

已核对 `Conversation.tsx` 的 Note → `RunNotice.tsx`：说明使用 React 文本节点直接渲染，无需新增纯文本组件或事件标记。本地命令说明直接复用该分支。命令无输出、未知斜杠命令最终无法分类时保留原始用户提问，而不是统一改成说明；只有记录明确证明本地执行时才归类为本地说明。

### 4.5 本批核心验收

| 场景 | 必须得到的结果 |
| --- | --- |
| 回答分三次写入，中间出现工具调用 | 同一轮有完整提问/工具/回答，不重复、不拆碎正文 |
| Stop 先到，最后答案后写入；下一轮随后开始 | 最后答案归原轮；新轮不吞掉上一轮答案、不改写其结束状态 |
| 自定义配置目录，nativeId 不同于 sessionId | 只读取绑定的官方历史，独立历史说明和聊天恢复限制保留 |
| JSONL 半行、UTF-8 跨段、完整坏行、截断/替换 | 半行等待；坏行可溯源且文件保留；替换不会静默跳过新内容 |
| 增量与全量同时触发、关闭、启动失败 | 没有重复导入、结束后追加或未释放 watcher |
| `/compact`、`/model`、自定义斜杠命令、`/clear`、`/resume` | 展示正确且不串官方历史 |
| 两个终端、多设备、隐藏标签、另一会话同步额度 | 各会话内容和游标隔离，不改变 owner/原生历史互斥 |
| 阅读旧消息时新记录到达 | 保留阅读位置，新输出提示沿用现有行为 |
| 下一轮问题先写入，上一轮回答首次迟到；分页/重载/导出 | 按 terminalTurnId 回到原轮，不因到达顺序错配 |
| 一条源记录生成多个事件，第二个事件写库失败 | 整条回滚、不广播半条结果，关闭仍可完成且原历史保留 |
| Stop 时有半行；退出末行是完整 JSON 但没有换行 | 前者等待追加，后者正常导入，不误判坏文件 |

先在 `terminal-history.test.ts`、`terminal-transcript.test.ts`、`terminal-controls.test.ts` / 现有集成测试建立关键复现。真实 SDK 读取临时 JSONL，不回退为把消息读取完全 mock 掉。PTY 和操作系统边界继续允许现有替代。

## 5. 第三批：多 Shell 与简化 ssh 使用

### 5.1 能力属于执行目标

新增有界 Shell 枚举与能力字段，参考上游但保留 CC Space 的 `viaSsh`、目标身份和现有握手。

| 目标 | 声明与默认 |
| --- | --- |
| Windows 本机设备 | PowerShell 7；只有检测并验证 Git for Windows 时增加 Git Bash；默认仍 PowerShell |
| 由 Windows 代理的 Linux SSH 目标 | 只声明适配器已经验证的 Bash，不继承本机 Shell |
| 原有 macOS/Linux 本机设备 | 沿用现有用户 Shell 探测与执行方式，不借机扩展目标支持范围 |
| 未提供新能力的旧客户端 | 沿用原执行合约，不猜 Git Bash 存在 |

Git Bash 检测吸收上游注册表、Git 所在目录、标准目录和 Scoop 路径，确认是 Git for Windows 的 `bin/bash.exe`；不将 WSL 的 `bash.exe` 或仅同名程序当成 Git Bash。探测失败不影响原 PowerShell 通道。检测结果与 `CC_DESK_TUNNEL_BASH` 等环境变量仅由主进程控制，不允许 renderer 指定任意可执行文件。

涉及：新增 `electron/git-bash.mjs`，调整 `windows-ssh.mjs`、必要的 `prepare-ssh.ps1/component-host.ps1` 环境传递、`proxy-bridge.mjs`、POSIX worker 和 `ssh-target-adapter.mjs` 的能力声明；服务端接入 `tunnel.ts/server.ts/store.ts`。

Git Bash 脚本仍经 stdin，保留 stdout/stderr/退出码。验证中文 Windows 原生命令输出、长脚本、空格中文路径、MSYS 路径转换和 `//c`，不能为编码修复改变用户全局代码页或系统设置。安装/移除 Git Bash 后通过重新连接刷新能力，不中途杀掉已有任务。

### 5.2 Shell 别名兼容旧会话

新增 `device-pwsh`、`device-bash`，POSIX 按已验证的 Shell 生成别名。**同时保留 `device-script`、`device` 和既有 `windows`**：

- Windows 的旧 `device-script` 固定保持原 PowerShell 语义，不随新偏好改成 Bash；旧提示词中的 PowerShell 脚本不能被送进 Bash。
- Linux SSH 目标的旧别名仍经过现有适配端点，并使用目标 `/bin/bash`、进程组取消和通道池规则。
- 新别名全部绑定同一个会话所属设备、同一端口/密钥/known_hosts 和原有通道限制，不能另开绕过认证的服务。
- 未检测到的 Shell 不生成有效别名，也不向 Claude 宣称可用。任务进行中偏好变化只影响后续说明，不更换执行目标或自动重放失败命令。
- 对保留的设备 Shell 别名采取显式失败处理：例如 Git Bash 已卸载后，旧命令 `ssh device-bash` 必须就地报“目标 Shell 不可用”，不能落入用户 SSH 配置或 DNS，意外连到同名主机。保留名集合与当前可用集合分开，包装器或配置只对这组确定的保留名阻止回退，不拦用户任意其他主机名。

### 5.3 偏好与设置界面

按当前服务下的设备 ID 保存偏好，沿用现有 SQLite 存储方式；不保存成全局 prefs，否则多服务、多设备会互相污染。服务端只允许当前认证设备修改自身偏好，不信任客户端随意传入的 deviceId。

Windows 桌面新增“设置 → Shell”，复用 `SidebarShell`、`.setting-row` 和标准选择控件；没有 Git Bash 时仍显示“未检测到”，提供安装后重连说明，不自动下载或安装。这里明确设置的是“这台电脑”，查看 SSH 项目时不能误改远程目标的 Shell。浏览器没有本机执行能力时不显示本机 Shell 控件。

偏好表示 Claude 优先选择哪个 Shell，另一个仍可用；默认保持 PowerShell，用户未设置时不强行改为 Bash。暂时检测不到此前首选 Shell 时保留用户选择并显示未可用，以实际能力为准向 Claude 描述，不偷偷永久改写偏好。

利用 `store.notice()` 在下一条消息更新实际 Shell 能力/偏好；更新维度包括同一设备的能力变化，不能只比较 deviceId 和路径。`prompt/told` 兼容旧元数据，`viaSsh` 不能在更新或设备改名时丢失。聊天 SDK 和原生终端共用设备描述；已打开的终端不靠改偏好重启，后续新进程/消息按实际支持的通知机制生效，UI 写明生效边界。

具体生效约定：聊天 SDK 在下一条正常输入收到通知；内嵌终端只在下次用户新开/重新打开该 CLI 时取得新的偏好描述，当前已打开 CLI 不保证随下一次键盘提交更新。服务端重连后可刷新实际可用别名，但不能假定这会更新模型记忆。新能力需在设备页、会话路由与 `prompt/told` 中传递；不能由当前窗口的设备状态覆盖会话所属设备的能力快照。

### 5.4 普通 ssh 命令：不破坏旧配置路径

吸收上游按会话生成 `ssh/scp/sftp` 包装脚本的思路，让新提示词可使用 `ssh device-pwsh`；作为本批最后一步实施。

- 保留 `sessionSshPath()` 现有 `<sessionId>.conf` 及原子更新方式。可在旁边新增 `<sessionId>/bin` 放包装脚本，继续指向该 `.conf`，不照搬上游删除旧 `.conf` 的迁移代码。
- 包装器只加当前会话配置并原样传递参数；解析真实系统程序时避免找到包装器自己。只在 Ubuntu 该会话的 SDK/PTY 子进程 PATH 前置，不改变服务全局 PATH、本机或 SSH 目标 PATH。
- `ssh -F <旧路径> device-script` 仍可用；验证经包装器重复显式传 `-F` 的旧模型命令，不产生递归或读错配置。
- 对非 `device`/已声明设备别名保留 Ubuntu 用户正常 SSH 配置。不能用 `device-*` 大范围占用用户其他主机名；配置按确切保留别名划分，并验证 OpenSSH 首值优先和 Include 顺序。
- 服务端 Docker 的项目卷挂载参数和目录权限必须允许执行这些脚本；离线预检和真实镜像验证这一点，不能只在 Windows 上看文件内容。
- 会话删除时只清理该会话的 `.conf` 和包装器目录，验证绝对路径归属，不动用户 SSH 配置。设备断线恢复只更新端点，不删除仍被会话使用的兼容配置。
- 提示词同时保留“目标不可用不回退 Ubuntu”“中断后不自动重试副作用”“凭据不可读入对话”等 CC Space 约束。不为了让命令变短削弱执行位置限制。

### 5.5 协议决策

CC Space 和上游当前均写协议 24，不代表新增字段自动兼容。上游将 `tunnel.credentials.shells` 改为必填，而本项目旧凭据 schema 是 strict，不能直接发送。

第一、二批优先复用已有事件，新增持久元数据不等于必须改变线协议；先验证现有混合版本读写，不预先承诺一定维持 24。

第三批采用现有握手能力协商方式增加 `deviceShells: { version: 1 }`（实施时确认名称无冲突）：服务端先声明，新客户端收到声明后才附加新凭据字段、发送偏好命令；未声明时使用完整旧消息格式与旧别名。新服务端将旧字段缺省映射到原能力。偏好界面没有能力声明时显示需配套升级，不发送未知命令。

协商落点固定为服务端发给主进程桥的第一份 `ready`：`proxy-bridge.mjs` 会先保存它，再处理 `tunnel.offer`、启动本地 SSH 和发送凭据，最终直到 `tunnel.ready` 才把 ready 交给 renderer。因此凭据字段裁剪必须在主进程发送前依据保存的 ready 完成，不能等待 UI ready 或凭据发送后的 tunnel.ready；SSH 后台桥同样走此流程。旧服务端收到的凭据逐字段与旧格式一致，新服务端只在完成凭据校验及 Shell 探测后向设备列表公布实际能力。

renderer 发来的 `device` 消息除现有 platform/viaSsh 外，也必须剥离新增 shells 等执行能力字段，重新由主进程注入；renderer 仅能通过受限命令选择已公布的偏好，不能伪造机器支持能力。服务端探测失败、旧客户端回连、同设备多连接能力不一致时，以该设备当前实际承载执行通道的连接为准，连接代次变化后废弃旧探测结果。

若第二批经复现需要 `terminalTurnId`，它是可选事件元数据，不作为权限依据；旧 UI 可忽略但无法保证新场景的轮次展示。候选发行应配套新客户端，明确旧 UI 的展示限制，并验证旧版本读取和重新保存后是否剥离字段。若剥离导致历史不可接受的退化，就纳入配套协议升级，不用“可选字段”掩盖回退损失。

如果这套双向兼容不能通过“旧客户端/新服务端、新客户端/旧服务端、SSH 后台连接”测试，则本批采用新的 CC Space 协议号和配套升级，不借用上游 24 放行。版本决策在打包前完成，禁止为复用旧包身份伪造协议或放松校验。

## 9. 第二轮审查结论与实施前实验

第二轮发现并在本文修正了以下设计缺口：初始快照与游标之间有丢记录窗口；SDK 的主链选择不能用简单行过滤替代；活跃半行会触发严格读取器报错；事件逐条事务无法保证单条源记录原子导入；仅靠回答 ID 不能关联跨轮迟到的首次回答；聊天通知不进入 PTY；模板升级可能一次性重读缓存；能力协商必须发生在凭据发送前；不可用 Shell 别名不能回退到其他 SSH 主机。
