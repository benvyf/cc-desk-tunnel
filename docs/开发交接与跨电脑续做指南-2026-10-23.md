## 7. 为什么失败过，目前怎么修

1. 原生自由问答不一定再次触发 `UserPromptSubmit`，因此加入 `PostToolBatch` 审核回答。
2. 权限弹窗 Tab 修改要求不一定触发普通提交，也不一定是失败工具结果。改成每个工具批次审核用户文本历史，不能只检查交互/失败工具。
3. Ubuntu `adf26f5` 仍失败：审核只看到旧提示，拒绝标记进入了模拟模型。VPS 的单次通过不能代替目标节点验收。
4. 隔离取证发现，Tab 新文字与本批工具结果存于同一条 user 历史记录，PostToolBatch 参数本身不含该文字。读取旧历史会产生放行缺口。
5. `ff57439` 要求读到本批每个 `tool_use_id` 的工具结果后才审核同一快照；未落盘时每 50ms 重读本机文件，最多 1 秒，超时阻断。这只重读磁盘，不重试 JEV 或 Claude。
6. 新增回归覆盖旧快照不触发审核、延迟写入的修改要求被拒绝、持久化超时不放行。相关 5 项测试和 TypeScript 检查通过。
7. `UserPromptExpansion` 不提供可完整审核的技能展开正文，因此**直接调用的自定义提示命令/技能展开暂时阻断**。`/compact` 有独立审核，不等于所有斜杠命令禁用。
8. PTY 故障输出改为 JSON 转义，避免日志中的控制码在显示时被终端执行。

官方受管策略在 `/etc/claude-code/managed-settings.json`，事件为 `UserPromptSubmit`、`PostToolBatch`、`UserPromptExpansion`、`PreCompact`，使用 `onFailure: "block"`。hook 配置应由管理员控制并只读挂载在 `/etc/claude-code/moderation-node.json`；未来激活复制既有节点凭据，不重新签发。

已知边界：每批审核及 SDK 聊天与现有门禁可能重复审核，**会增加 JEV 用量和延迟**；command hook 本身不额外调用 Claude。审核文本限制 64KiB，历史文件限制 16MiB，超限拒绝。官方可能将被拒绝文本留在历史，后续全历史审核可能继续拒绝；不能偷偷编辑历史绕过。普通外部文件、图片、技能描述、工具输出、宿主机管理员/直接 SSH 不是本门禁的全面隔离范围。
