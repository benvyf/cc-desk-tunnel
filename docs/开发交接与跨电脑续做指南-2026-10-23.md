## 2. 已确定的需求与边界

### 2.1 内容审核方向

- 用户希望别人只使用 CC 客户端；强制检查放在 CC 服务端，不能依赖客户端隐藏按钮或前端自律。
- 管理员设置关键词，命中可疑内容后调用 JEV 模型进一步审核；直接拦截规则、触发规则、例外和误判处理仍需明确。
- 讨论过模型名称 **jev-latest**，实际 API 地址、认证方式、分类、阈值和超时策略尚未定稿。不能凭这个名称直接接入生产。
- 对要求模型审核的请求，审核超时或不可用不能默默放行。
- 普通客户端不展示审核状态、审核结论详情和拒绝原因。拒绝后应结束操作并返回通用失败，不得一直等待或伪装成执行成功。管理员另行查看真实原因。
- 原生终端、远端命令执行、配置和指令文件等可能绕过聊天入口，必须单独评估。只审核一个发送消息事件不能等同完整防护。
- 参考 Wei-Shaw/sub2api 的相关机制，按需要借鉴，不整体照搬整套系统。

当前 VPS 的 CC 中转转发加密的 TCP/TLS 流量，不能直接读取聊天正文。因此审核执行点应在能拿到明文的 CC 服务端；VPS 可以承担后续集中策略与记录管理。

### 2.2 维护和发布方向

- 定制源码来源：[benvyf/cc-desk-tunnel](https://github.com/benvyf/cc-desk-tunnel)。上游更新先审查、合入定制分支、检查冲突和回归，再由管理员发布。
- 官方发布新版本不能让定制版提示或安装官方更新。不要恢复原有官方更新链路。
- 安装包由自己的 VPS 托管，更新索引由管理员离线签名，客户端只信任打包固定的源和公钥。
- 首版在线更新只面向**相同协议的 Windows x64 客户端**，不负责批量升级六台服务端。
- GitHub Actions 曾因账号账单问题无法启动任务。这不是已确认的代码测试失败，也不阻止本地构建、离线签名和 VPS 分发；本方案不要求先开通付费 Actions。

## 9. 接下来按什么顺序做

### 第一步：实现交付 C，先把可控更新闭环完成

以下为 C 的实施顺序；控制器、IPC、界面、打包、隔离真实升级及原生交互取消重试验收现已完成，源码已提交推送并从清洁提交构建正式引导包，当前需由管理员生成生产签名索引并发布 pilot。进度以 [C 实施计划](superpowers/plans/2026-10-23-update-client.md) 为准，范围限于客户端和打包，不重复部署 B，不重新生成生产密钥：

1. **打包身份**：固定 product、origin、公钥、channel、正整数 build、protocol、源码提交；缺少或非法配置时拒绝启用更新。首个引导包不能拿旧预览 EXE 改清单冒充。
2. **主进程控制器**：固定源请求、验签、防回放状态、每个安装的共享缓存和进程锁、受限下载与取消；不依赖 CC 服务端的广播或连接就绪。
3. **新 IPC 与界面**：增加受限 managed-update:* API 及“关于与更新”，renderer 不可传入任意 URL、文件路径或版本执行安装。旧 IPC 和 CC 服务端升级命令保持拒绝。
4. **安装协调**：安装前重新获取并验签活动索引、重算完整文件 hash、检查缓存真实路径；协调同一安装的全部连接窗口、运行任务、终端和登录流程。状态不明就不安装，不静默杀任务。
5. **pending 与完成确认**：安装前记目标 build、原 build 和安装器 hash；由新程序的内嵌 build 确认成功，取消或失败保留诊断记录，不提前显示成功。
6. **契约及真实 Electron 测试**：使用临时测试签名身份，覆盖恶意元数据、IPC、下载篡改、撤回、并发与失败恢复。生产私钥不用于自动化测试。
7. **专用 Windows 安装验收**：实际完成 build 1 → build 2 安装、启动确认、取消和失败。单独解包启动不能替代安装验收；不直接覆盖用户当前客户端。
8. **发布**：先做同协议 pilot，验收后 stable。19 → 20 人工引导与服务端迁移单独处理。

必须保持的设计约束（详见总设计，实施时以完整契约为准）：

| 项目 | 约束 |
| --- | --- |
| 版本判断 | 正整数 build 递增；不是只比较 appVersion；应用版本仍为三段式 |
| 协议 | 仅相同协议在线安装；不匹配只提供管理员配套迁移提示 |
| 元数据 / 制品 | 索引最多 64 KiB，安装包最多 1 GiB，Ed25519 + size / SHA256 |
| 时效 | 索引最多 7 天，建议每 3 天续期 |
| 防回放 | revision 单调；同 revision 仅允许同 payloadHash；同 build 身份不可变 |
| 网络 | 固定 HTTPS 源和路径；元数据不重定向；制品重定向仅同源 HTTPS 且位于固定前缀 |
| 网络栈 | 主进程使用 Chromium 网络栈，遵循系统代理 |
| 安装缓存 | %LOCALAPPDATA%/CC-Desk-Tunnel/updates/{installationId}；由规范化可执行目录计算，不使用每连接 userData 作为产品锁 |
| 查询节奏 | 启动延迟 30 秒，每 6 小时；手动至少间隔 30 秒；元数据超时 10 秒 |
| 下载 | 单连接 20 秒，空闲 15 秒，连续 5 次无进展失败，整体最多 30 分钟；严格校验 Range |
| 安装退出协调 | 最多 15 秒；超时取消；不杀运行任务 |

### 第二步：第一台服务端配套试点，然后才扩展六台

完成 CC 服务端镜像在 Linux 的独立验收，重新采集第一台及 02–06 真实版本，备份数据、配置、镜像、客户端和证书基线。管理员人工进行第一台协议 19 → 20 迁移并验证回滚路径，再决定其余节点。

不要把“新通道能更新 Windows 客户端”扩展解释为“普通客户端可以升级服务器”；服务端更新权限继续由管理员掌握。

### 第三步：再开发内容审核与统一管理

先对齐 GhostAPI 线上源码和现有业务定制，再确定关键词策略、JEV 接口、审核失败行为、日志保留与管理员权限。梳理 CC 所有可触发模型和执行的入口，把服务端拦截放到真实执行前，定义普通客户端通用错误行为。完成单节点试点后，再推进集中策略、记录和节点管理。

审核不能仅靠关键词完整识别恶意用途，也不能靠更新签名约束原生终端；对应访问控制需要独立设计和验收。
