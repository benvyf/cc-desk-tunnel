- 第一轮镜像导出报 unpigz CRC32 mismatch。清理失败候选和构建缓存后，第二轮构建结束，但候选校验失败；原服务仍在线运行 Build 14。
- 用户隔离检查中，Node 24.22.2、官方 CLI SHA256、发行清单、入口脚本、运行环境等级和 SDK 版本均符合；235 个程序文件只有 `apps/server/web/assets/UniGB-UTF16-H-DKjbEwc0.bcmap` 摘要不符。这是 PDF 中文字体映射资源。
- 正确大小 44,086 字节，SHA256 `386fd39581245c034da016a92d23f3df1117d169f996100050b264fc09a84e35`；镜像中同大小文件摘要为 `42e646ab0434918f52852ee8d5c1223e2c9cba7ae4fcc8b5bb5c30515f9c7fa9`。

- 内核输出有 memory pressure 提示，所提供的日志中未见直接 I/O 故障或 OOM kill。不能据此确认硬件损坏、内存不足为唯一根因或笼统归为软件缓存。保留后续系统排障边界。

## 最小恢复路径

`scripts/repair-build16-candidate.py` 只适用于 ubuntu-cc、已存在的 Build 16 staging 和精确候选标签 `cc-space-runtime:build16-baff75da710a-c0627fd6a4fd`：

1. 持有原升级锁；核对发行清单精确摘要及源资源摘要，拒绝链接路径。
2. 检查候选没有被任何运行/停止容器引用。用无网络、只读临时容器核对 Node、CLI 摘要、清单、SDK、入口和全部文件；必须只坏已确认的一个资源，否则停止。
3. 用本机已核对的镜像 ID 建立临时专用标签，构建上下文仅含 Dockerfile 和正确资源（约 44 KiB），只执行 `COPY --chown=0:0`。不再次运行 npm、不改运行环境、不启动模型、不修改业务挂载。
4. 完整复检通过才保留修复后的本地候选；失败恢复原标签并保留日志。临时基底标签非强制移除，Docker 保留候选需要的共享层。签名归档、descriptor 和已发行包不改。
5. 用户再新建 Build 16 升级任务，原签名安装器仍会完整复检候选、离线预检、重新核对空闲和空间、冷备份、切换与失败恢复。维护工具不代替这条路径，不允许跳过校验。

该处理恢复的是已确认的单文件候选损坏，不是对内存/磁盘/解压问题的根治。若小层恢复或完整复检仍异常，应保留新日志，进一步检查宿主机，不能继续叠加修复或忽略错误。
