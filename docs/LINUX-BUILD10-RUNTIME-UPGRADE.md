# Linux Build 10 基础镜像升级

目标：服务端 0.3.7 / Build 10 / 协议 23，Node 24.22.2，受管运行时 `node24-cli2.1.295-v2`。配套 Windows 客户端为 Build 25。Claude CLI 2.1.295、SDK 0.3.286 保持不变。

本轮仅支持 `ubuntu-cc`、`ubuntu-cc-02`、`ubuntu-cc-03`。04、05、06 不纳入。旧 Build 4/5/8/9 的程序描述符、锁文件、官方 CLI、只读管理策略和容器结构必须符合已登记基线；未知环境会停止，不覆盖数据。

## 获取并执行命令

待管理中心发布 Build 10 后，打开 `https://api.ghostapi.org/cc-updates/admin/updates`，在 Linux 配套服务端区域确认 **Build 10 / 协议 23**，复制“清理并升级基础镜像（ubuntu-cc / 02 / 03）”命令。

三台使用同一条完整命令，由脚本识别主机名和容器。建议顺序：第一台成功并用配套客户端验收，再执行 02，最后执行 03。不要使用之前复制的 Build 9 命令，也不要执行上游项目的一键安装命令。

执行前结束所有聊天任务、后台任务和等待审批的任务，并关闭原生终端，包括空闲的原生终端。普通客户端连接不必手动退出，脚本在确认空闲后会自动断开并暂时阻止重连。升级期间保持 Ubuntu 控制台打开。

流程：校验当前基线和签名 → 仅清理未使用的 Docker 构建缓存 → 检查准备及备份空间 → 验证 Node 下载固定摘要 → 在原镜像基础上构建新程序和依赖、保留原官方 CLI → 无网络、无账号、零 CLI 调用的离线预检 → 复制并校验独立审核策略 → 暂停并检查无任务 → 断开连接、停止原服务 → 冷备份 → 切换镜像和策略 → 就绪验证。

更新后的宿主机脚本在准备前额外检查空闲状态，在构建和预检后再次清理未使用的构建缓存并重新测算空间；进入停服前会冻结服务复核任务和容量。备份与恢复路径处于不同文件系统时分别核算。空间不足输出 required、available、missing 字节，保持原服务。冷备份写出后读取并核对文件摘要，验证通过才切换；下载短暂失败最多尝试三次，签名及校验失败不重试。旧 agent 必须按 HOST-UPDATES.md 重新接入才能获得这些脚本改进，已签名的 Build 10 业务包不被替换。

成功输出为 `UPGRADE_OK: Linux Build 10 / protocol 23` 和 `4/4 SUCCESS`。无需再执行“已接入服务端升级”或“首次接入”命令，也无需重新登录 Claude。重复执行已安装的相同版本只验证并返回 `ALREADY_INSTALLED`。

普通程序更新无法完成这次 Node 和依赖的升级；它应返回需要升级基础镜像，不得绕过校验。

## 配套客户端与回退

协议 22 的旧客户端不能连接本次协议 23 服务端。准备好 Windows Build 25 安装包，再安排节点切换；本轮未升级的 04/05/06 仍使用其原有兼容客户端。

备份和离线回退放在 `/var/lib/cc-runtime-upgrade/backup-*`。成功或失败时均保留打印的实际备份目录和回退命令。不要删除原容器、原镜像、原策略目录和冷备份；不使用全局镜像 prune 清理回退资源。

失败时脚本沿用已验证的原容器恢复流程。若需手动回退，先结束新服务上的任务和连接，再执行此次输出的 `sudo python3 <实际备份目录>/rollback.py --rollback <实际备份目录>`；回退程序无需再次下载。不要将示例占位符直接复制到终端。

## 发布边界

Git 合并不等于中心已发布。必须先将已校验的 Build 10 签名包、兼容管理中心命令和续期登记上线，再给用户实际命令。原有 Windows 发布通道、登录用户、工作空间、监控/审核节点配置保持原样；不会代用户升级三台 Ubuntu。
