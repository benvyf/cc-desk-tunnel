# 管理中心更新与升级流程改进方案

日期：2026-11-03（香港时间）。状态：用户已批准方案；代码实现及验证完成，待确认中心发布与首台节点采用窗口。

## 目标与范围

用户在管理中心确认具体设备和目标版本后，自动完成可安全执行的清理、准备、断开空闲客户端、更新和结果验证，减少需要手动操作的中断。覆盖普通程序更新及已审核的基础镜像升级。当前基础镜像迁移仍仅支持 ubuntu-cc、02、03，不扩大到其他节点。

不承诺任何环境下必定成功：磁盘确实不足、正在执行任务、签名异常、备份损坏等情况必须停止；停止时应明确旧服务是否仍运行、是否已恢复，以及下一步操作。

## 已核实的现状

- 生产 Build 10 迁移脚本在构建前执行 Docker builder prune，并校验“数据文件逻辑大小 × 2 + 2 GiB”。
- 新镜像构建和离线预检后，切换脚本校验“数据文件逻辑大小 × 2 + 512 MiB”，此前没有再次清理构建缓存。
- 本次失败发生在创建冷备份目录、暂停旧容器之前，未进入切换。
- 节点清理构建缓存后，根分区空闲从约 2.5G 增至 6.0G。
- 普通更新通过服务管理接口进入维护准入，目前仍拒绝活动连接。
- 宿主机 agent 和基础迁移支持脚本由接入安装器复制到 Ubuntu，VPS 更新不能直接替换已有节点文件。
- 本地 source 的当前工作区有其他任务修改，且当前分支未包含全部线上宿主机更新代码；实施前须核对线上来源并隔离开发。

## 方案比较

1. 仅补构建后清理：改动最小，解决本次磁盘问题，但普通更新仍需手动断开客户端。
2. 分阶段升级流程（推荐）：统一准备与切换规则，保留普通更新、基础迁移各自已验证的备份和回退机制。改动覆盖入口、准入、脚本、日志与现有节点接入。
3. 重写全部更新器及任意阶段自动续跑：范围过大，容易引入重复切换或重复恢复，本次不采用。

## 推荐流程

### 1. 校验目标和现场

锁定用户确认的设备、Build、协议和 SHA256；保留签名、发布时效、受信来源、防降级和单任务锁校验。识别同一版本已成功安装的情况，验证身份与就绪状态后直接返回成功。

读取当前服务状态及未完成的切换记录。存在无法判定的恢复状态时，停止并指向原记录，不开始另一轮清理或切换。活动任务、后台任务、等待审批和原生终端均视为忙碌，尽早提示，避免白做构建。

### 2. 安全清理与容量预算

基础镜像升级清理未使用的 Docker 构建缓存。程序自身临时文件仅允许清理能够证明未被当前容器、候选镜像、策略挂载、正在执行的作业或回退记录引用的对象；无法证明时保留。第一版可以只清理构建缓存，不增加自动删除历史目录的策略。

不自动清理旧镜像、停止的容器、卷、业务数据、账号凭据、备份、日志或策略目录。不采用全局 system prune，也不绕过空间校验。

容量按文件逻辑大小和实际目标文件系统计算，分别覆盖准备、备份和恢复路径。输出清理前后空闲字节、所需字节和不足字节，显示易读单位。普通程序更新使用其实际阶段的空间预算，不照搬镜像构建预算。

### 3. 在旧服务运行期间完成准备

下载和验证签名归档；下载遇到临时网络错误可有限重试，默认最多三次并设置超时。签名错误、摘要不符、目标版本变化或运行环境不符直接停止。

复用经过身份验证的候选镜像，否则构建并执行离线预检、复制和验证策略。在基础镜像构建完成后，再清理一次未使用的构建缓存，再执行最终容量检查。

准备期间不主动断开客户端。最终切换前重新核对原容器身份、配置、策略、数据大小和空间，防止准备过程中的变化使旧检查失效。

### 4. 维护准入与自动断开空闲连接

普通更新应通过明确授权的维护接口，同步关闭新任务、新终端和客户端重连准入，并再次检查所有活动。保留现有严格安装入口的默认行为，宿主机维护入口使用现有宿主机身份，不增加任意命令入口。

基础迁移继续使用现有冻结容器并检查进程及会话状态的机制。确认无活动任务后，断开空闲客户端并阻止重连，再停止服务。

若发现活动任务或原生终端，撤销本次维护准入并保留原服务；不终止 Claude 任务、不强杀终端、不自动关闭审批。提示具体阻碍类别，用户结束活动后重新确认更新。

维护准入必须覆盖检查与断连之间的竞态；不能先断开连接，再在无保护的窗口里检查任务。

### 5. 备份、切换和验收

保留各更新路径原有的一致性备份及离线回退机制，备份完整性验证通过后才切换。基础迁移保留原容器、原镜像、原策略和业务数据冷备份。

成功要求目标 Build、协议、发布摘要、运行时身份及服务就绪状态均匹配；仅进程启动或健康接口返回 200 不视为完成。确认成功后解除维护准入，允许客户端重新连接；协议不兼容时明确显示所需配套客户端版本。

### 6. 失败和中断处理

- 准备失败：保持旧服务运行，清楚标记“尚未切换”。
- 准入检查失败：撤销本次维护状态，保留服务和已有活动。
- 切换后失败：沿用原回退事务并验证原服务恢复；只有验证通过才能显示“已恢复原服务”。
- 恢复失败：显示“需要人工恢复”，提供实际日志、备份位置和经过记录确定的回退命令，保留现场。
- 宿主机重启或进程被终止：根据持久阶段记录检查实际服务状态，不自动重放安装。可验证已提交目标时回报成功；恢复所需信息不充分时要求人工处理。
- 自动重试仅限下载等无副作用步骤；不自动重复执行数据切换或回退事务。

## 管理中心展示

进度显示“校验目标 → 清理缓存 → 准备并验证 → 检查空间 → 进入维护/断开连接 → 备份 → 切换 → 验证 → 成功/恢复结果”。普通更新跳过镜像构建阶段。

页面以实际状态说明“旧服务仍在运行”“正在维护”“已恢复原服务”或“需要人工恢复”。磁盘不足时显示空间缺口；任务忙碌时显示阻碍类别；完整日志继续保留在宿主机。

## 已接入节点的采用方式

实施时同时修改发布源码、宿主机安装包、升级命令及文档，校验嵌入支持脚本的固定摘要。先在测试环境验证接入替换与失败恢复，再为现有节点提供一次性的宿主机程序更新方式。

优先复用现有接入安装器进行一次接入更新；明确这一步不触发业务升级。不得仅更新 VPS 后宣称现有 Ubuntu 已采用新流程。无需为本次修改新增通用 root 自更新系统。

先完成可审阅代码和测试，再确定中心发布和首台节点的维护窗口；不自动升级其他机器。

## 验收

1. 复现本次“准备前足够、构建后不足”场景：构建后清理并重新计算；仍不足时明确缺口，旧服务不停止。
2. 空闲客户端在线时，两种更新路径均能自动断连；维护期间自动重连及新增任务不能穿透准入。
3. 执行中任务、后台任务、等待审批和原生终端均阻止切换，且准入正常恢复。
4. 下载短暂失败按上限重试；签名、摘要或身份校验失败不能进入切换。
5. 备份失败、切换失败、新服务就绪失败时验证各自恢复行为，不能误报成功或恢复成功。
6. 不同挂载点的容量按真实路径校验；断电中断记录、重复确认、同版本重试和锁竞争均不会造成重复切换。
7. 使用构建缓存共享镜像的测试，确认候选镜像、当前服务和所有回退资源可用。
8. 验证新装与已接入宿主机的脚本更新、摘要一致性、凭据保留/失败恢复，并验证管理中心阶段与结果展示。
