# CC 本地浏览器与 Ubuntu 出口

状态：2026-10-25 用户已选择本地内嵌浏览器方案，并接受管理员在客户端首次登录本人 Claude 账号。用户随后授权逐步实现并逐步验证；当前开始实现[代理服务端基础](../../claude-web-proxy.md)，完整本地浏览器及真实Ubuntu联调尚未完成或部署。原 noVNC/RFB 代码、测试和联调包保留作历史试验，不作为本方案的实现或验收证据。

## 用户使用方式

- 左上角沿用 Chat / Coding 切换，保留 Coding 任务与草稿。
- Chat 在本地 CC 中显示真实网页，本地完成排版、滚动、选字、输入和复制；不传输远端桌面画面。
- 网页访问经已有 CC 的已认证加密连接送到 Ubuntu，再由 Ubuntu 连接官网。浏览器断线时停止网站访问，不改成本地直连。
- 管理员在此客户端的专用浏览器中人工完成首次网页登录，后续复用本地独立 profile。仅账号本人使用自己的账号；不复制 CLI 凭据或 Ubuntu Chrome 的会话。
- 登录失效时暂停使用，提示管理员在该客户端人工处理；不自动登录、不通过后台发消息保活。初期保留人工“登录需要处理”入口，自动识别须另经验证。
- 普通使用不需要远端 Windows 打开查看器；远端 Windows 若承载 Ubuntu 虚拟机，仍需保持宿主和网络运行。

## 数据路径

```text
本地 CC 专用浏览器
  → 仅该浏览器使用的本机回环代理
  → CC 现有公网入口上的独立认证加密通道
  → Ubuntu 的受限目标连接
  → Claude 网站及经管理员核验的必要网站域名
```

官网 HTTPS 保持浏览器至网站的端到端加密，Ubuntu 只转发连接。不安装自签官网根证书、不伪造官网证书、不解密网站 TLS。不调用私有接口、不重写网站业务逻辑、不修改指纹来规避风控。用户已授权本地显示规则隐藏左下角设置/账号区，该项在网页嵌入后单独实现和验证，不改变官网业务请求，也不作为账号权限控制。网站看到的是经 Ubuntu 出口访问的本地浏览器，不能承诺网站把它识别成 Ubuntu Chrome，也不能据出口地址承诺账号不会受限制。

网页 DOM、Cookie、网站存储、缓存和下载文件位于本地；出口位于 Ubuntu。此方案不再满足“网页登录凭据仅存 Ubuntu”的旧条件，用户已接受管理员在客户端首次登录。

## 实现边界

使用与 CC 控制界面隔离的 Electron WebContentsView 和专用持久 session；不开 Node 权限、不向官网暴露 CC 的 preload 或 IPC。官网不能读取服务凭据、管理能力或 Coding 草稿。网页新窗口及登录跳转必须留在相同受控浏览器会话中；不能交给本机默认浏览器形成出口旁路。

为该 session 配置专用回环代理，代理在首个网页请求之前生效。回环代理采用每次连接随机凭据，凭据仅由主进程提供给所属浏览器会话。通过验证服务证书的 CC 通道传输目标连接；服务端先认证、限流和检查准入，再解析并连接目标。现有 system-proxy.mjs 是客户端连接 CC 时使用 Windows 系统代理的辅助代码，不是现成的 Ubuntu 网页代理，不能原样用于本方案。

Ubuntu 限制 HTTPS 目标端口443、必要域名及公共目标地址；默认不准入任意目标。不允许客户端通过此通道访问回环、内网、链路本地或云元数据服务。部署时的目标域名清单由管理员依据正常人工登录与使用的必要请求核验；验证阶段先使用自有测试域名，不为收集清单自动遍历官网。解析在 Ubuntu 完成，对解析结果逐次检查并使用已核验地址建立连接。

断开 CC、代理认证失败、错误证书或远端不可达时，销毁网页目标连接并显示故障；无 DIRECT 回退。不自动重复提交消息或上传。需要覆盖 DNS、IPv4/IPv6、QUIC、WebRTC、服务工作线程、跳转、新窗口和下载的出网路径；单纯设置一次 session.setProxy 不能作为全部出网受控的验收证据。具体 Electron 限制能力先通过离线验证；无法约束的通路应关闭或阻止该功能，而不是允许本地访问。

浏览器本地原生输入避免远端输入法适配；中文仍需实测兼容性，暂不新增专门输入法桥接。附件下载至本机采用所属浏览器会话的下载流程，须验证仍走远端通道；不自动打开或执行文件。上传、语音、第三方登录等网站功能不能仅凭内嵌成功即宣称全部兼容。

## 审核与部署

现有 Coding 的 JEV 强制审核保留。本地渲染与透明 HTTPS 转发不会自动提供网页消息正文审核，因此不能把改用代理当成解决审核覆盖的办法。只要当前部署要求强制覆盖网页输入，真实 Chat 仍须拒绝准入；该阻塞在生产启用前单独解决，不通过移除审核配置或解密官网 TLS 来绕过。

设计目标是复用现有 CC 公网 TLS 入口，不新增公网代理端口，也不为正式使用强制要求 VPN。现有生产服务没有新增代理协议，需要受评审的客户端和服务器配套更新，不能只在现有客户端填一个代理地址即可启用。用户本机无法直连 Ubuntu 私网 SSH、目前只有 UU 管理通路，是独立回环测试的限制，不等同于正式 CC 公网通道不可用。

原蓝色画面联调及 cc-browser-network-lab.tar.gz 不再需要传送或运行。未在本次改动中停止、删除远端真实浏览器、变更其登录目录或部署任何新服务。

## 验收顺序

1. 用自有 HTTPS 测试站完成本地 Electron → 认证 CC 通道 → Ubuntu 的请求，核对网站观察到的出口，并验证官网 TLS 证书未被替换。
2. 对比本机和 Ubuntu 两侧的连接记录，覆盖 DNS/IPv6、跳转、下载及断线场景；恶意目标、未认证连接和本地直连均应拒绝。初期不访问 Claude。
3. 检查官网视图与 CC 权限隔离、Chat/Coding 切换、原生输入和本地文件流程，验证失败时不重复提交操作。
4. 生产审核准入问题解决并完成配套交付审查后，由管理员人工进行一次实际需要的网页登录，验证关闭重开后的 profile 和失效维护流程。不读取或迁移 Ubuntu Chrome 的 Cookie。
