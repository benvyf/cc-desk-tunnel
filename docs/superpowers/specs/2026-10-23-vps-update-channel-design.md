# VPS 定制更新通道设计

日期：2026-10-23。设计基于 `fd6e2130ccff8070d3349963c0997b2b21b9f79d` 的更新隔离实现。用户已选择使用自己的 VPS 保存安装包、发布定制更新，并要求普通 CC 客户端不能升级服务端。

本文完成当前第 1 步“发布规则和权限边界设计”。它描述后续实现契约，不代表 VPS 服务、在线升级或管理网页已经实现。现有关闭在线更新的试点包保持原行为。

## 1. 目标与首版范围

首版提供 Windows x64 定制客户端的版本查询、管理员发布与撤回、用户确认下载及安装。只接受管理员签名且符合内嵌发布通道的定制包，不查询 GitHub，不回退官方源。

CC 服务端继续拒绝 `service.update.check` 和 `service.update.install`，Docker 继续固定执行镜像内 `/app`。服务端镜像构建、备份、安装和回滚由管理员执行。六台服务端的网页批量升级需要独立的节点部署机制，另行设计，不复用普通 CC 会话或让 CC 容器控制宿主 Docker。

首版不实现内容审核、GhostAPI 数据库或二进制改造、跨协议自动迁移、强制静默安装、Windows 代码签名或自动密钥轮换。审核状态和拒绝原因仍只属于后续管理员功能；客户端更新提示可以正常显示。

签名校验限制产品自带的在线更新入口，不撤销用户、管理员或原生终端现有的文件与命令执行权限。后续审核方案仍需单独处理这些权限，不能以启用签名更新宣称已阻止所有客户端或服务端替换。

## 2. 方案选择

| 方式 | 优点 | 局限 |
| --- | --- | --- |
| **同一 VPS 的独立更新服务，Nginx 分发文件** | 可逐步加入发布网页；下载支持断点续传；不依赖 GitHub 账单或 GhostAPI 匹配源码 | 需维护独立目录、管理权限和备份 |
| VPS 仅提供静态文件，完全通过 SSH 发布 | 组件少，适合少量手工发布 | 后续做网页发布时仍需增加管理服务 |
| 直接修改现有 GhostAPI 提供更新功能 | 可共用界面和身份系统 | 当前缺少与运行二进制完全匹配的源码，直接替换存在运维风险 |

采用第一种。更新服务部署在现有 VPS 的独立程序和数据目录，Node 管理进程仅监听回环地址，Nginx 处理 HTTPS 和只读安装包分发。后续 GhostAPI 可添加管理入口；在单独的身份整合设计完成前，不声称已经单点登录，也不通过 URL 传递 GhostAPI token。

## 3. 构建身份与版本比较

保留 `apps/desktop/package.json` 的三段式应用版本，例如 `0.3.6`，不在现有解析链路中直接加入 `-custom` 后缀。增加独立的定制构建身份：

| 字段 | 规则 |
| --- | --- |
| `product` | 固定 `cc-desk-tunnel-managed` |
| `build` | 全局递增正整数，管理员分配，已发布后不可复用；首个支持 VPS 更新通道的发行包使用 1 |
| `appVersion` | 三段十进制字符串，对应应用和 NSIS 版本 |
| `protocol` | 与打包源码的 `PROTOCOL_VERSION` 相等 |
| `sourceCommit` | 构建时清洁 Git 工作树的完整 40 位十六进制提交 |
| `platform` / `arch` | 首版固定 `win32` / `x64` |
| `channel` | 管理员打包时固定为 `pilot` 或 `stable` |

是否存在新客户端只比较 `build`，同时验证产品、通道、平台、架构和协议。即使应用版本仍为 0.3.6，定制 build 2 也可以更新 build 1；官方 0.3.7 不属于本发布通道，不参与比较。UI 在关于页面显示应用版本和定制构建号，避免只看 0.3.6 而混淆来源。

构建身份、更新 HTTPS 基地址和可信公钥由打包器写入应用资源；其来源作为审核过的非秘密构建配置纳入源码。缺少有效 HTTPS 地址、构建身份或公钥时，启用在线升级的发行构建直接失败。开发模式保持禁止安装，不用环境变量、服务端消息或渲染进程参数临时覆盖发布源。

已生成的 `managed-preview-fd6e213` 不分配追溯构建号，不重新解释为 build 1，也不覆盖其 SHA256 清单。新增通道实现完成后重新生成首个发行包。

## 4. 发布路径与数据契约

使用管理员配置的 HTTPS 源及固定路径前缀 `/cc-updates/v1/`。具体域名和 TLS 在 VPS 部署预检时从管理员配置读取；本设计阶段不创建 DNS、证书或签名密钥。

公开接口为：

```text
GET /cc-updates/v1/channels/pilot/win32-x64.json
GET /cc-updates/v1/channels/stable/win32-x64.json
GET /cc-updates/v1/artifacts/{build}/win32-x64/{filename}
```

这些是只读公开内容，不包含服务 token、API Key、节点地址或用户数据；客户端查询不上传设备标识、对话和凭据。管理接口需要单独的管理员权限，普通下载权限不授予上传或发布能力。

元数据响应采用 JSON 信封：

```text
schema     = 1
keyId      = 内嵌可信公钥表中的标识
payload    = 发布载荷 UTF-8 JSON 原始字节的标准 Base64
signature  = Ed25519 签名原始字节的标准 Base64
```

签名字节固定为 `UTF8("CC-DESK-TUNNEL-UPDATE-V1\n" + keyId + "\n" + payload)`。验证器按接收到的 payload 字符串验签，不通过解析后重新序列化 JSON 验签。信封字段严格匹配，未知字段拒绝；Base64 必须是规范编码，解码再编码应等于原字符串；Ed25519 签名必须为 64 字节。先检查响应长度和内嵌 keyId，再验签，最后解析载荷及语义。

签名载荷包含以下严格字段：

| 字段 | 类型与语义 |
| --- | --- |
| `schema` | 整数 1 |
| `product` | 固定产品标识 |
| `channel`, `platform`, `arch` | 与当前客户端固定配置完全相等 |
| `revision` | 每个通道/平台/架构的递增正整数；发布、续期和撤回都增加 |
| `issuedAt` | UTC 时间，不得晚于客户端当前时间 5 分钟以上 |
| `expiresAt` | UTC 时间，必须晚于客户端当前时间和 issuedAt，且相对 issuedAt 的有效期不超过 7 天 |
| `state` | `published` 或 `empty` |
| `release` | published 时为下述对象；empty 时必须为 null |

`release` 对象字段：`build`、`appVersion`、`protocol`、`sourceCommit`、`notes`、`filename`、`size`、`sha256`。所有整数必须为正的 JavaScript 安全整数；notes 最多 8,000 字符，以纯文本显示；SHA256 为 64 位小写十六进制；filename 必须精确等于 `CC-Desk-Tunnel-Setup-{appVersion}-x64.exe`。安装包最大 1 GiB，元数据响应最大 64 KiB，notes 不含可执行 HTML。

下载路径完全由内嵌基地址、已验证的 build、平台、架构和 filename 推导；载荷不允许任意 URL 或路径。HTTPS 元数据请求禁止跳转；下载的跳转仅允许同一个 HTTPS origin、无用户信息和相同 `/cc-updates/v1/artifacts/` 路径前缀。更换发布域名需要重新分发带新配置的引导包。

## 5. 签名与发布权限

签名工具在管理员电脑对清洁提交生成的文件计算大小、SHA256 并签名。私钥保存在管理员指定的源码树外受保护目录，不写入 Git、安装包、VPS、GhostAPI、客户端配置或日志。客户端仅内嵌公钥。清单签名解决本更新通道的发布真实性；它不等同于 Windows Authenticode，也不会消除未签名安装器的系统提示。

VPS 管理服务只接收已签名清单和对应文件，独立验证签名、大小和 SHA256 后才能发布。管理网页的“发布”操作是激活上传的签名候选，不由网页保存私钥或任意重签安装包。发布日志记录管理员、时间、build、revision、提交和制品哈希，不记录管理凭据。

公开目录只读挂载到 Nginx；管理服务仅能写自己的制品和索引目录，无 Docker socket，不读写现有 GhostAPI 的配置、数据库或六台服务数据。管理 UI 的身份验证、会话和 CSRF 在该服务的实施设计中独立完成，不使用 CC 服务凭据授权发布。

首版仅信任内嵌公钥，不从网络自动接受新公钥。更换或丢失签名密钥时先人工分发新引导客户端；私钥被盗时停止发布并使用人工可信渠道恢复，不承诺凭旧签名即可安全恢复。

## 6. 发布、续期、撤回和回滚

发布流程：构建并测试 → 管理员签名 → 上传候选目录 → VPS 独立验签/校验 → 将完整制品移动到不可变 build 目录 → 原子替换通道索引。并发激活按通道加锁，revision 不递减，禁止修改已存在 build 的制品内容。

先向 pilot 发布并验证，再用管理员新签名、stable 自身递增 revision，将同一制品哈希发布到 stable。客户端不自行切换通道。首次部署可配置一台试点电脑使用 pilot，其余电脑留在原版本，待验证后再分发 stable 引导包。

签名索引有效期至多 7 天，建议每 3 天在管理员电脑重新签名续期，即使没有新 build 也增加 revision。到期不自动使用缓存安装，也不打断正常 CC 会话；管理界面展示即将到期状态。未来改进签名运维可另行评估，首版不把私钥搬到 VPS。

撤回须上传并激活更高 revision 的签名索引，`state=empty`、`release=null`。客户端在启动安装器前必须重新读取有效签名索引，确认仍发布同一 build、size 和 hash，否则废弃待安装项。撤回不能逆转已完成的安装，也无法瞬间取消刚跨过最终检查的离线安装器；管理员界面应明确此边界。

每个安装基目录保存已接受的最高 revision 和最高已成功观察到的 build，更新安装共享同一产品目录的连接进程时共用锁。拒绝低 revision；相同 revision 只接受与已记录 payload SHA256 完全一致的载荷。持久记录通过临时文件和原子替换写入，不放在单个服务连接的独立目录下。

锁、缓存和持久记录放在 `%LOCALAPPDATA%/CC-Desk-Tunnel/updates/{installationId}`，其中 installationId 是 Windows 下规范化、大小写归一后的实际可执行文件所在目录的 SHA256。同一安装的所有连接共享此目录；不同解包目录的试点程序使用不同目录。不得从 renderer 传入 installationId 或缓存位置，也不以当前连接的 user-data-dir 作为安装身份。

默认拒绝安装 build 不大于已安装/已确认 build 的包。最高已观察 build 是另一条防回退下限：重复查询或重试同一尚未安装的候选允许，前提是 build 不低于该下限、制品身份相同且仍高于已安装 build；这不代表允许重复安装。续期可以修改 notes，但不能改变同 build 的版本、协议、提交、文件名、大小或 SHA256。修复回滚采用“旧的已验证源码 + 新 build”重新构建并重新签名，不能只给旧二进制换一个清单 build。该方式不保证旧源码兼容新版本用户数据，管理员需要另行核对数据回滚。首版自动回滚和强制降级都不开放。

## 7. 客户端工作流

Electron 主进程负责固定源访问、验签、兼容性判断、下载、文件校验和启动安装器。渲染进程只能调用“查询、下载、安装已验证候选、取消”语义，不传入源地址、URL、任意版本字符串或本地 EXE 路径。

建议新 IPC 使用 `managed-update:state`、`managed-update:check`、`managed-update:download`、`managed-update:install`、`managed-update:cancel` 与状态订阅，处理函数仍经过现有 file renderer 来源校验。旧 `service:upgrade`、`update:install`、`release:notes` 保持拒绝，避免恢复原来可操作服务端或按任意版本联网的边界。

状态顺序：disabled / idle → checking → available → downloading → ready → installing；没有候选时回到 idle，失败时进入 error 并允许有界重试。状态显示在客户端“关于与更新”，与当前 CC 会话连接状态独立，不依赖登录成功或服务端 ready/update 广播。

启动后在没有待结束安装事务时延迟 30 秒查询，之后每 6 小时查询；手工查询最短间隔 30 秒。元数据超时 10 秒，失败不自动下载，无网络时仍允许正常使用原客户端。后台同一产品安装只运行一个查询/下载任务，多窗口读取共享状态；应用完全退出后不要求后台常驻更新服务。

用户确认后才开始下载。下载使用 Chromium 网络栈以遵循现有系统代理，临时文件存入该安装产品共用的更新缓存，文件名由本机生成。复用既有下载节奏的合理部分：单连接最长 20 秒，空闲 15 秒终止，连续 5 次无进展后失败；同时设置整次下载 30 分钟上限。Range 响应必须核对起点和总长度，若服务器返回 200 则从零重下；文件增大立即拒绝。完成后流式校验完整大小和 SHA256，再原子转为 ready 文件。

安装前重新验签最新索引并重新计算安装文件哈希，确认路径仍处于本机专用缓存且不是符号链接/重解析到外部文件。存在运行中的任务、原生终端、账号登录流程或无法确认状态的其他连接窗口时，安装按钮不可执行；不静默杀任务。所有属于同一安装的连接进程退出后，才以既定安装参数启动已验证 EXE，不经 shell 拼接用户输入。退出协调超时 15 秒则取消安装并保留当前客户端。

安装前写入 pending 记录，保存目标 build、原 build 和安装器 hash。新程序启动后以自身内嵌 build 确认安装结果，再提升成功观察到的 build 并清理 pending。用户取消安装、安装失败或新程序没有启动时保留可诊断记录，不提前声称成功，也不删除原客户端资料。

## 8. 协议与首次引导

首版只允许 `release.protocol === installed.protocol` 的在线安装。签名有效但协议不同时可显示“需要管理员配套迁移”，不提供下载/安装动作。仍验证并记录索引 revision，不以此信任其软件包。协议检查由主进程强制执行，不能只靠 UI 隐藏。

用户回传第一台是 0.3.5 / 协议 19，实际运行 `/app`；定制源码和已生成试点包为 0.3.6 / 协议 20。两者之间必须在 Linux 验证、生产备份和服务端配套准备完成后人工引导迁移。现有官方客户端和关闭在线升级的 fd6e213 包，都不会因为 VPS 放置了文件而自行具备新通道。

默认不覆盖共享电脑上的旧客户端来测试协议 20。试点应使用单独解包目录及独立 user-data-dir，保留连接其他协议 19 节点的原客户端；正式替换安装需在管理员确认配套服务兼容后执行。

## 10. 验收标准

1. 本地生成临时测试密钥，证明合法签名可验证，篡改任意字段、换 keyId、未知字段、非规范 Base64、错误 hash/大小、过期和未来时间均拒绝；测试不使用生产密钥。
2. 同版本更高 build 可更新；错产品、错通道、错平台、错架构、不同协议、低 revision、同 revision 不同 payload、已安装或更低 build 均不会获得可安装候选。尚未安装的同一候选允许重复查询/重试，但不得低于最高已观察 build，同 build 的制品身份不得改变。
3. 并发上传、制品校验失败或发布中断，不暴露不完整文件或半成品索引；更高 revision 的撤回会使旧待安装候选失效。安装器已启动的撤回边界有明确说明。
4. 下载中断可受限续传；错误 Content-Range、跨域跳转、超量响应、写入失败、下载总超时和文件篡改均不能执行 EXE。
5. 真实 Electron 测试使用已打包程序和 loopback 固定测试注入，验证新 IPC 不接受任意 URL/路径；旧更新 IPC 及服务端更新命令继续拒绝。运行任务和多窗口状态不明时不安装。
6. 使用专用 Windows 测试环境完成 build 1 → build 2 的实际安装、启动确认、用户取消和失败保留；当前用户电脑不直接覆盖已安装客户端。仅启动解包程序不替代安装测试。
7. 在测试 Linux 构建独立更新服务并验证 HTTPS、Range、管理鉴权与无现有服务数据挂载；校对实际域名、TLS 和公钥后再安排 VPS 部署。
8. 先 pilot，再 stable。旧官方版本和 fd6e213 试点包的人工引导、协议 19→20 的配套迁移与回滚单独验收。
