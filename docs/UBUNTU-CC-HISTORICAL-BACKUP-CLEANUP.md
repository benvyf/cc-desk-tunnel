# ubuntu-cc 历史冷备份退役

2026-11-06。用户授权清理 `ubuntu-cc` 只保留必需资源，避免旧升级资源长期占用 30 GiB 磁盘。当前失败任务为 Build 15 的切换前空间准入：需要 4,352,589,126 字节，可用 3,131,965,440 字节，缺少 1,220,623,686 字节；当前服务仍为 Build 14。

## 依据与策略

用户提供的清单显示：第一台保留了早期 pilot/monitor/bootstrap、原生终端、0.3.7、消息审核和 runtime 多代冷备份，每代约 207–846 MiB；构建缓存已经为零。这与 02/03 的已用空间差异有关，不能靠重复 APT/build-cache 清理解决，也不能直接删除整个 /var/lib/cc-*。

`scripts/retire-ubuntu-cc-backups.py` 是一次性、针对已授权第一台的维护工具，不修改已发行 Build 15 归档或签名，不自动执行节点升级。其范围：

- 必须以 root 在主机名 `ubuntu-cc` 执行；与运行时升级使用同一个 `upgrade.lock`，升级进行中拒绝清理。
- 确认当前容器健康、未暂停；只接受能以安装记录的 containerId/imageId 唯一对应当前运行版本的已完成冷备份。验证该备份 SHA256、原始配置、独立 rollback.py/helper.py，以及所需前一代容器仍退出且镜像身份一致。
- 保留上述完整必要回退。不是按日期选择“最新”，不是只看文件存在，也不以本机已用空间少为由取消回退。
- 在固定历史升级目录中，仅计划退役 `data.tar`、`data.tar.gz`、`old-image.tar`、`source-config.tar`。不删除目录、账号、配置、会话、项目、未知文件、日志或记录；不跟随符号链接，不处理有多个硬链接的归档。
- 所有容器（包括已停止的历史容器）挂载覆盖的备份目录均跳过。任何未完成的恢复/切换记录会阻止清理；删除前复核容器身份/挂载和文件身份，没有全局 prune、没有 Docker rm/rmi。
- 历史归档按用户授权退役后，那些旧代的完整数据回退不再可用；保留记录和 `RETIRED-BACKUP.json` 明确标识，并在升级根目录保存 root-only 清理审计。所保留的当前版本必要回退不受影响。

脚本默认只列计划，显式 `--apply` 才执行。清理完成报告真实剩余空间，不能把归档逻辑大小当成磁盘必然释放量。即使释放了历史备份，后续升级仍须通过构建预算、冷备份和恢复空间检查；不保证任意数据增长下 30 GiB 永不不足。

## 验证与执行边界

本地 5 个测试中 4 通过、1 个真实 flock 场景按 Windows 条件跳过。远端 Ubuntu 对同组测试 5/5 通过，包含真实临时目录 apply：只删除计划归档，保留必要冷备份/元数据/日志/挂载，生成完成审计；健康变化、缺失回退、损坏摘要、符号链接和未完成记录被拒绝。Docker 查询为隔离替身，不清理 VPS 或生产节点，未调用 Claude。

由于 Windows 不能直连目标 Ubuntu 的 SSH，本轮工具并未在生产 `ubuntu-cc` 实际执行。需要用户在该 Ubuntu 下载固定提交对应脚本、核对 SHA256 后执行 `sudo python3 <已校验脚本> --apply`。实际释放多少以该机输出为准。普通升级自动清理仍保持既有引用保护，本工具不会暗中改变其他机器的回退保留策略。
