# 登录时提示升级客户端

2026-11-04，香港时间。按已批准方案及 karpathy-guidelines 实施；当前为未发布候选，线上中心及 Ubuntu 业务服务未改变。

## 已实现

- 管理中心在认证和工作空间授权通过后、签发连接票据前检查目标节点的可信当前协议。在线且稳定的宿主机心跳才用于判断；最新“可升级版本”不会冒充实际运行版本。离线、过期或升级中的观测仍交由握手判断。
- 当前已部署的邮箱客户端省略版本信息，按其协议 22 基线兼容处理。需要更新时返回 426、可读升级说明及结构化要求，不替换原票据、不清除保存登录；401/409 含义不变。
- 新客户端由主进程提交实际 Build 和协议。内嵌身份独立保留，即使更新缓存或检查中断也不会把当前客户端误判为旧版。
- 使用一个现有 Modal 风格的升级提示：“此工作空间已更新，请升级 CC SPACE 客户端后重新登录。你的账号和聊天记录会保留。”支持下载和稍后升级，覆盖单/多工作空间及自动登录。
- 下载入口复用既有验签、发布范围、防重放与制品路径计算，仅接受所需协议；有匹配且较新的签名版本才提供浏览器下载入口。点击时再次核对发布，不自动安装、不关闭客户端或升级服务端。既有自动安装仍拒绝跨协议更新。
- 握手保留稳定的 version_mismatch 错误帧并添加可选 requiredProtocol。旧客户端可继续读原文字；新版明确区分客户端过旧与服务端过旧，不再把前者引向“检查服务端更新”。同协议的较旧 Build 不强制更新。

## 修改范围

复用已有 DesktopAccess、HostUpdates、ManagedController、Electron IPC、ProxyClient 和 Modal。仅新增一个界面组件，未引入新的更新框架、数据库表、配置开关或 CSS 系统。原协议号及认证规则保持不变；requiredProtocol 为可选字段。

## 采用与限制

管理中心候选需要单独发布；新版客户端候选需要正式编号、签名登记和发布。服务端握手文案及可选协议要求字段需随签名服务端候选采用。协议契约文件变化会影响既有签名兼容摘要，应沿用受控的配套发布流程，不能用相同 Build 覆盖现有归档或绕过基础镜像准入。

现有 Build 24 可以在新版中心处显示明确的升级文字，但不能远程新增专用弹窗；新弹窗需安装本次或以后具备此能力的客户端。当前 Windows 公开 pilot 仍为 Build 24／协议 22，本次没有发布候选。先准备并验证匹配客户端，再安排工作空间协议升级。
