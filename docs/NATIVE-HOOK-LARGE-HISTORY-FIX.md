# 新消息审核范围与 02 历史故障修复

日期：2026-10-30，香港时间。状态：源码与配置模板已调整，尚未打包或部署；Git 提交与推送状态以仓库记录为准。

## 用户最终确定的范围

只审核聊天或原生终端中新发送的消息原文。不附带会话历史、额外上下文或自动生成的提示；不审核独立的问答回复、权限补充、压缩说明、全局说明修改、工具输出或模型输出。

CC 聊天在服务端接收 `message.send` 时审核，明确通过后才能保存/发送；重复请求 ID 仍按原有规则去重。`run.continue`、`session.compact`、`approval.reply` 和 `instructions.update` 不再调用该审核，也不再拼接历史。

终端以官方 `UserPromptSubmit` 新消息事件为边界，完整审核事件中的 `prompt`。如果官方 CLI 把某段文字重新作为普通新消息提交，则按新消息处理；独立问答/权限/压缩事件不接入，不靠文字关键词猜测来源。明确的 `source=user` 优先于继承的 SDK 环境或代理标记，不能据后两者跳过真实用户消息；未知来源明确拒绝。机器来源与无明确用户来源的子代理事件不纳入；旧版没有 source 字段的交互提交仍审核当前 prompt。

## 实现

- 删除原生钩子的历史读取、流式扫描、全文拼接、历史大小限制、写入等待与游标需求。即使 transcript_path 指向 17 MiB 的损坏历史，新消息也只按自身文本审核；钩子不会打开该路径。之前的流式方案与相关竞态处理已由这个更小的方案替代。
- 64 KiB 限制只约束本次消息的 UTF-8 字节数，不截断消息，不累计旧文本。超限明确提示缩短本次消息；新建会话不再被当作解决单条消息过长的办法。
- CC 聊天已在 SDK 之前审核，因此 SDK 的 command hook 不再重复调用审核。CC 的实际 SDK 子进程使用官方 `CLAUDE_CODE_ENTRYPOINT=sdk-ts` 标识，实际交互 CLI 使用 `cli`，均在对应子进程环境里最后确定，避免误继承另一个入口标记。没有伪造客户端类型或改变官方 CLI 字节。这个入口区分用于 CC 的执行流程，不作为防止机器所有者自行启动其他进程的安全边界。
- 保留现有 VPS 的节点/会话/策略版本/完整文本缓存。新范围没有引入历史检查点、持久化放行文件或新的数据库。
- 新消息遇到拒绝、接口故障、无效结果或超时仍停止发送；不自动重试。未改变 Claude 原生工具审批和账号登录流程。
- 新配置只注册 `UserPromptSubmit`，保持 `onFailure: block` 和十秒命令超时。独立管理员钩子不属于本次 CC 范围调整，不自动删除。
- 失败只输出阶段、稳定错误码与合法格式的会话编号，不输出正文、凭据、完整路径或原始异常。错误码为 `native_review_input_limit`、`native_input_failed`、`native_config_failed`、`native_review_failed`。stderr 留存仍取决于官方 CLI 的日志设置，客户端错误码可供定位。

## 配置迁移与上线

需要同步更换程序和管理员策略。启动/终端开启检查发现任何非 `UserPromptSubmit` 事件调用 CC 审核脚本时会要求迁移，包括原有 `PostToolBatch`、`UserPromptExpansion`、`PreCompact` 以及额外注册，避免无关的大工具结果继续启动钩子并触发原有 stdin 大小保护。脚本对普通大小的已知旧事件可直接返回成功，但这不能代替移除旧注册。

新安装使用 `deploy/docker/managed-settings.json` 和 `deploy/configure-moderation.py` 的单事件模板。配置器重新配置时会从部署配置的 `MANAGED_CONFIG_DIR` 读取受保护的原策略，或读取已有默认策略；只替换 CC 自己的注册，保留混合组中的独立钩子、matcher 和其他设置。旧外部策略目录保留不动，新目标文件沿用原有备份、原子写入与失败回滚，重复配置保持幂等。若登记的外部策略缺失则停止，不能默认为空并丢掉独立规则；若旧策略全局禁用钩子则停止，不悄悄启用其他管理员钩子。

已有节点必须在空闲维护窗口核实实际挂载与部署配置，停止旧程序后，才将新策略与新镜像一起离线预检、切换。配置器不会负责停止容器或证明填写的部署配置就是当前 live mount；这些仍是镜像切换入口的职责。不要在旧程序继续提供服务时先单独替换策略。回滚时恢复匹配的镜像与策略。

备份恢复路径另行补齐：`manage.sh restore` 在解压前要求 root；`tar --no-same-owner` 后仅把应用数据交回 UID 1000，保留 `.managed` 管理员策略/凭据的 root 所有权，不跟随数据目录中的链接改动外部文件。随后再导入恢复的节点配置并迁移旧 CC 注册。原先整目录递归 chown 会使新配置器拒绝已恢复策略，已在 Linux 复现并修复。

钩子、策略检查和 SDK 适配都属于受管程序的兼容性保护文件，管理员策略固定运行 `/app` 的脚本。因此需要包含最终源码的新基础镜像与对应的新签名 Build，不能用普通在线业务更新冒充修复生效。当前旧升级脚本只接受历史固定镜像，不能直接拿它处理已经升级的 02 Build 8；后续发布前需核实真实镜像/挂载并准备匹配的切换入口。旧四事件试点/实验脚本是历史验证材料，不作为此范围的新部署入口。

保留账号、会话、凭据、TLS、审核阈值与关键词。先在 02 试点，由用户用原先报错的旧会话正常发送消息验收，再安排其他节点。现有旧节点在实际升级前仍使用原来的审核范围。

最终定向 review 复现并修正了明确用户消息被继承标记跳过、配置器覆盖独立策略两项问题，并增加外部策略来源、混合钩子组保留、原策略备份、迁移幂等、失败恢复、全局禁用不误启用的回归。验证结果：本机 84 项 Node 回归通过；配置器 17 项中 14 通过、3 项 POSIX 跳过。VPS 临时目录中的 Linux 核心/部署测试 15/15、配置器 17/17 通过，临时目录自动清理，未加载生产配置或账号。TypeScript、代码格式及 diff 检查通过。
