# Windows Build 22 / Linux Build 8

版本 0.3.7，协议 22，pilot 通道。此次提交包含当前全部客户端、服务端及管理中心待发布改动：终端尺寸与输入响应、更新布局与检查时机、登录保留、聊天运行状态、排队与插话、消息导航波峰、可拖动侧栏。

## 服务端升级入口

管理中心「客户端更新」展示已签名的 Linux Build 8 和对应升级命令。已经运行协议 22 且兼容当前基础镜像的受管节点，使用「已接入服务端升级」。执行前结束任务并退出所有客户端连接，等待命令明确报告成功或回滚。

仍使用已审查 Build 4 基础镜像的第一台 `ubuntu-cc`，使用「终端基础镜像升级」；该命令同时包含安装与离线回退脚本，校验原镜像、依赖、签名、归档与目标 Build 8。未知镜像拒绝执行，不能把第一台专用基础镜像命令用于其他节点。单独运行 `scripts/upgrade-terminal-base.py` 默认只进行准备，`--install` 才切换。

新装命令用于尚未接入的已审查节点，不能作为现有节点升级的替代。上述操作不重新登录 Claude，也不发送模型请求。

## 管理中心的兼容部署

短期服务端维护授权需要 Build 8 的节点支持。现有中心已部署记住登录续期，但节点尚未升级时，不能提前切换维护授权逻辑。

因此先发布 Build 8 服务端归档、升级命令和 Build 22 客户端；中心命令更新基于当前生产提交，只同步命令所需文件，保留旧节点的既有授权方式。完整新中心归档另行准备；待节点升级完成后切换，启用无需永久服务凭据的维护授权。记录生产中心的实际提交，不把主分支全量源码误标为已全部部署。

## 发布与回退

构建必须来自干净提交，包内 build、协议和 sourceCommit 与签名索引一致。新安装包使用独立 Build 22 路径，将 pilot 和管理中心下载入口指向新包；保留 Build 21 的原始文件，不覆盖旧 build 的身份与 hash。服务端 Build 8 同样使用独立路径。更新 VPS 两套自动续期的精确登记，保留 stable 状态。

用户本机安装和 Ubuntu 节点升级由用户随后执行，发布过程不代为重启节点或测试真实模型。
