## 发现并修正

| 级别 | 问题 | 修正与证据 |
| --- | --- | --- |
| P1 | supervisor 的 runtimeCheck 仍接受标记 1，而镜像和迁移要求 2，导致后续普通更新被错误判为基础迁移 | 统一为已审核的标记 2；从实际 main.ts 提取回调，在隔离环境用真实打包标记和模拟受保护文件元数据执行，复现原错误并验证修正 |
| P2 | 准备/忙碌检查安全失败后，旧服务仍就绪，但 failed 阶段使管理中心永久拒绝再次提交 | supervisor 提供事务已结束且已提交子进程仍存活的 retryable 证明；agent 同时要求 serving 为真才向中心报告可重试。测试实际 Python current() → HostUpdates SQLite 队列，其他未就绪/无证明状态仍拒绝 |
| P2 | 回退途中两次数据目录移动没有可继续的记录，中断后重复回退被已有保留目录阻止 | 持久记录私有恢复目录、数据目录身份和阶段；校验并同步恢复树后才移动。根据实际身份区分尚未移动、已保留候选数据、已放回旧数据；未知目录拒绝覆盖 |
| P2 | 回退的空间/校验失败发生在停止候选之后，且暂停回执丢失后会再次暂停并收到 409 | 在候选仍可运行时准备恢复；冻结检查后先隔离网络再解除暂停并停止；已暂停容器跳过重复暂停。失败检查不擅自解除原有暂停 |
| P2 | 接入时非 active 的既有 unit 停止失败会被忽略；接入被拒后旧 agent 重启失败只显示原 HTTP 错误 | 既有 unit 的停止失败阻止消耗接入码；重启需检查返回码和实际 active 状态，否则明确报告通道恢复失败，保留原文件 |

## 回归覆盖

- 回退在解压后、保留候选目录后、旧数据放回后中断，执行相同恢复命令均可继续。
- 候选数据保留在预期位置，未知当前目录或保留目录不覆盖。
- 恢复空间不足时尚未暂停或停止候选服务。
- 暂停实际成功但回执丢失时，重试不会再次暂停；原来已暂停且忙碌时不擅自解除暂停。
- 正常就绪的旧服务在安全失败后可接受新的人工确认；未就绪、事务未结束或旧版本无证明时继续拒绝。
- 安装器停止和重启失败均有明确结果，不把尝试恢复当成恢复成功。

## 采用边界

新版宿主机脚本需通过中心发布与 Ubuntu 一次重新接入采用。普通更新的运行时修正、retryable 证明和 supervisor 新能力必须进入后续签名服务端/基础镜像发布；不得覆盖既有 Build 10 的签名归档来替换代码。旧版保持原严格更新方式。
