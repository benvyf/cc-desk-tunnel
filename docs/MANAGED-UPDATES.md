# 定制版维护与更新

当前状态和跨电脑恢复步骤以根目录 [DEVELOPMENT-HANDOFF.md](../DEVELOPMENT-HANDOFF.md) 为准。定制源码基于 0.3.6／协议 20，已合入 GitHub 更新分支；工作分支为 `codex/account-monitor-production`，完整当前源码通过交接 Git bundle 提供，普通 GitHub clone 可能仍是较旧阶段。

## 已上线的维护方式

- 管理中心统一顶部导航，账号监控、客户端更新、内容审核各有独立页面；账号页只读 VPS 缓存。
- Windows pilot 已发布完整 Build 5；Linux 配套完整程序包为 Build 2；两者版本 0.3.6／协议 20，源站和公钥固定在 `deploy/managed-client.json`、`deploy/managed-server.json`。
- 客户端更新使用 VPS 签名索引，核对 Build、协议、源码和安装包摘要，经用户确认安装；不自动跟踪 GitHub/Fork Releases。
- Linux 签名包只更新兼容的程序和配套 Web。客户端不匹配时显示“升级配套服务端”，检查精确目标、空闲和兼容性，备份、切换、验证就绪，失败恢复旧程序并保留当前业务数据。
- 历史普通升级入口和任意发布源继续隔离；新受管 API、IPC、签名和用户确认是独立权限边界。
- Windows 与 Linux 分别登记精确发布身份，由 VPS systemd 定时续期签名索引；续期不改变安装包 Build，不自动推进 stable。

## 已有节点怎么接入

第一台 Ubuntu 实际业务容器已经是 0.3.6／协议 20，用户已安装被动账号监控，但尚未完成受管服务端升级的首次 bootstrap。请在管理中心客户端更新页复制最新首次接入命令，关闭 CC、结束任务后在该 Ubuntu 控制台执行。该入口仅支持审查过的第一台 profile；其余五台暂停。

首次接入验证旧容器的运行环境、审核策略、持久化实现和目标签名；隔离预检通过后保存冷备份并替换容器。后续兼容的程序升级由客户端确认执行。监督程序和固定 CLI／SDK 属于镜像边界，不能把业务程序升级当作任意运行环境迁移。

依赖、持久化格式、审核 hook 或运行环境不兼容时，明确要求人工镜像升级。`/opt/cc-desk-tunnel` 旧宿主源码仍可能是 0.3.5／协议 19，不能据此重建覆盖现有运行容器。真实节点首次安装和失败恢复尚需用户控制台验收，隔离测试不代表实机已完成。

## 发布与恢复

1. 比较上游变更并合入开发分支，保留审核、监控、固定更新源和兼容性边界。
2. 用 Node 24、锁文件和干净提交完成检查、离线测试与完整配套构建；新程序用新 Build，已发布 Build 保持不可变。
3. 把源码 bundle 和精确制品传到 VPS，由 VPS 私钥签名；先 pilot，核对 stable 字节未变化。管理令牌和签名私钥不下载到开发电脑。
4. 更新管理中心运行包前备份、暂停两套续期 timer，并明确确认两个 oneshot 服务均不在运行或过渡状态。
5. 发布后登记新 expectedRelease、干净源码和独立制品路径，验证强制续期与两个 systemd 沙箱，恢复双 timer；完整下载核对大小／hash、签名及首次命令摘要。
6. 回滚程序和配置时保留当前业务数据。冷备份供人工核对恢复，不能自动用旧数据库覆盖新写入。
