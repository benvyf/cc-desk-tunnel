# 定制版维护与更新

本仓库以 `benvyf/cc-desk-tunnel` 为定制源码来源，当前基线为上游 v0.3.6（协议 20）。本阶段关闭产品在线更新，尚未加入内容审核，也未迁移生产服务。当前修改尚未发布为安装包。

## 更新策略

- 客户端不显示更新按钮、更新公告或协议不匹配后的升级操作；不匹配时提示联系管理员安装配套定制版。
- 服务端拒绝客户端发来的检查与安装更新命令，不查询发布页，不广播或下载客户端安装包。
- Electron 拒绝旧的更新、安装与发行说明 IPC。只隐藏界面不是这里的权限边界。
- Docker 固定运行镜像内 `/app`，忽略数据目录 `program/` 的历史更新。旧文件保留，不删除会话、配置或安装包。
- `manage.sh client` 与 `manage.sh release-token` 停用。旧 `PROXY_RELEASE_REPO`、`PROXY_RELEASE_TOKEN`、`PROXY_PROGRAM_DIR` 不会重新启用更新。

这些限制针对 CC Desk Tunnel 自带的更新通道。此阶段未改变原生终端、远端命令执行和配置权限；它们需要在后续集中审核与访问控制阶段继续评估。Claude Code 的更新控制仍沿用现有配置。

## 后续维护方式

1. 将官方仓库作为上游参考，更新先合入开发分支，检查与定制改动的冲突，不直接覆盖生产程序。
2. 固定已审核提交，使用 Node 24 和锁文件安装依赖，完成项目检查、测试和配套构建。
3. 由管理员分发同次构建的客户端与服务端。未来自建发布通道另行实现，当前不会自动跟踪 Fork Releases。
4. 备份数据、部署配置、现有镜像和客户端安装包，先迁移一台并验证，再处理其他机器。使用 `manage.sh upgrade --from` 仅代表管理员手工替换镜像，程序不会验证输入归档是否属于定制版，须由管理员核对来源和校验值。
5. 回滚时恢复已保存的配套镜像与客户端；数据回滚须核对备份与版本兼容性。

六台现有服务实测协议为 19，而本源码协议为 20。必须先采集第一台的实际安装版本、备份并验证迁移，不能直接把本源码覆盖到六台服务。当前电脑没有六台 Ubuntu 的直接 SSH 入口，后续采集仍经远端 Windows 逐台执行。

首次定制发布前，请不要执行 README 中面向 Releases 的安装命令。发布时应包含配套服务端归档、客户端安装包、校验清单和基线提交标识；不要以官方同名版本包替代定制构建。
