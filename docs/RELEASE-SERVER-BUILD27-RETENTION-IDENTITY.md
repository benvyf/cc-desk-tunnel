## 原因和修复

受管 selected_container 从 Docker ps 得到短 ID，后续 Docker 操作支持该 ID，但 retain_previous_backup 把它原样交给按 `/Name` 查找当前容器的保留代码，触发无文字的 StopIteration。于是必要回退验证与旧备份轮转提前停止；原日志只显示空的 RETENTION_PENDING 原因。手动节点名称路径没有暴露这个问题。

27 从已验证标签、唯一匹配的 Docker inspect 结果返回规范容器名称，供主流程和保留代码一致使用；不改变基于原始容器完整 Id、镜像 Id、冷备份摘要和挂载引用的保护。异常诊断增加类型名，空消息也能定位。新增已发行 Build 26 精确描述符/CLI/依赖准入，保持 protocol 24 / node24-cli2.1.325-v5 / Node 24.22.2 / CLI 2.1.325 / SDK 0.3.286。

不降低空间预算、不跳过备份、不改写摘要，不把宿主机 Disk 0 的 I/O 重试和已观察到的备份字节不一致说成已经修复。Build 26 包保持原字节，修复必须通过新 Build 27 提供。管理中心已审核 v5 / Build 26+ 接入规则和 v6 首次安装器继续适用，不需要再修改公开旧入口。

## 定点验证和边界

使用原已发布 26 的 selector 和真实 preserved_rollback 验证函数复现短 ID 导致清理提前退出；修复后同一链路验证通过。新回归覆盖短 ID →规范名称→实际必要回退验证→镜像轮转参数；零/多个代理仍拒绝；手动节点选择保持；空消息异常保留类型。其余相关 Linux 默认清理、备份与引用保护回归、真实制品和签名链验证记录于发行证据。

受控重试前已保留原失败记录、摘要、磁盘事件及公开静态文件的精确错误字节。另从签名 Build 3 原文件按用户回传的偏移 26052 / 97→124 重建错误静态文件，SHA256 与用户备份内文件 b080db… 完全一致；该重建明确不是从用户归档传回的数据，不含账号/历史。正常保留流程可按现有规则轮转非必要的旧归档，但不能把它们记为校验成功或代替必要回退。

本轮不再自动提交另一安装任务。27 发布完成后由用户在管理中心确认新目标；整份冷备份必须通过后才允许切换。宿主机存储问题仍需另外处理，升级成功也不能当成硬件修复证明。
