# Ubuntu 设备更新按钮

管理中心「账号监控 → 我的设备 → 更新设备」支持普通程序更新和基础镜像升级。

## 首次接入

1. 在目标设备面板点击「生成宿主机接入命令」，复制命令。
2. 在对应 Ubuntu 宿主机控制台执行。需要 Ubuntu 24.04、Python 3.12、OpenSSL、Docker 和 sudo。命令与主机名绑定，十分钟有效且只能使用一次。
3. 返回管理中心，等待「宿主机更新通道在线」和当前版本出现。安装通道不会自动更新 CC 服务。

接入范围仍按实际运维授权执行；本批首先接入 ubuntu-cc、ubuntu-cc-02、ubuntu-cc-03。现有 Build 10 基础镜像迁移脚本只支持这三台的已知部署。

## 日常更新

先结束运行任务、关闭原生终端；普通程序更新还需要断开客户端连接。在面板检查目标版本，点击更新并确认具体设备和版本。目标设备主动领取任务，执行后上报结果；可展开「更新进度与恢复指引」查看日志尾部。

普通更新复用现有服务端更新准入、签名校验和回退流程。Build 10 基础镜像升级复用已审核的清理、冷备份、迁移和恢复脚本。后续不兼容的基础镜像发布必须在已签名且完整校验的服务端归档中携带 `deploy/host-update/apply.py`，接受 `--release <release.json> --install`；没有该迁移程序时拒绝自动执行，使用该版本的人工部署说明。普通程序更新无需迁移程序。

## 权限边界

宿主机更新程序由 root 管理，通过 HTTPS 主动连接管理中心，每约 15 秒轮询一次；执行期间约 5 秒报告一次。无需开放 SSH，也不把 Docker socket 或宿主机授权令牌交给 CC 容器或客户端。管理中心确认请求只能指定已发布版本和 SHA256，不能下发任意命令。设备自行验证发布签名、时效、发布身份和防降级条件。

- 程序：`/opt/cc-host-updater`
- 私有配置、持久任务回执：`/var/lib/cc-host-updater`
- 任务日志：`/var/lib/cc-host-updater/jobs/<任务ID>.log`
- 服务日志：`sudo journalctl -u cc-host-updater.service -n 100 --no-pager`
- 停用通道：`sudo systemctl disable --now cc-host-updater.service`（正在更新时会等待工作进程结束）

管理中心仅保存宿主机令牌的哈希；浏览器只获得一次性接入命令，不获得长期令牌。Nginx 需添加 `deploy/update-service/nginx.conf.example` 中的 `/cc-host/v1/` 入口。

重新接入时，安装器先校验文件，再停止原通道；中心接受接入后才替换本机程序和凭据。接入码被拒绝时保留原文件并尝试启动原通道。如果中心已接受接入但响应在网络中丢失，旧凭据可能已经失效，需要重新生成接入命令执行；这不会触发应用升级。

## 中断和失败

同一设备只能有一个待处理任务。未被设备接收的任务十分钟后失效，查看设备状态或重新生成接入命令时也会清理过期等待，不需要设备重新上线；通道离线时管理中心会显示等待连接。任务首次派发时即记录为已领取，避免执行过程中误按等待超时解锁。设备收到已经超过确认时限的任务会报告失败，不执行安装。已开始的任务不因页面关闭而取消。

宿主机进程或机器中断后，持久回执会报告失败，**不会自动重放更新**。先检查任务日志和其中的备份、回退指令，确认服务状态后再决定是否重试。重装通道前如检测到未处理的运行回执会停止安装，避免覆盖恢复线索。更新成功必须核对目标 Build、协议和就绪阶段；仅下载或仅启动不视为成功。
