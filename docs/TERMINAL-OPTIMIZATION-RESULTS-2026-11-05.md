## 实施结果

| 项目 | 结果 |
| --- | --- |
| A1 SSH 收尾 | 桌面端正常 EOF 等待剩余数据与关闭握手，10 秒未完成才销毁；错误和主动取消仍及时清理。没有替换已修复的服务端收尾逻辑。 |
| A2 终端与聊天衔接 | 最终历史成功读取、原生 ID 与当前聊天相同、没有切换历史时，补记 `native.context`，恢复压缩入口。使用该 PTY 配置目录的历史元数据，避免 SDK 默认目录与实际终端目录不同。 |

| D 缓存管理 | 按方案留在后续独立工作范围。未新增缓存提醒或会发起模型调用的空闲自动压缩。 |

## 先复现、后修复

- 关闭握手被接收端暂停时，旧桌面实现提前销毁 stream，未完成通道被立即遗忘；新增真实 TCP/WebSocket 测试先失败，修复后通过。另验证约 1 MB 中文/emoji 尾部完整、正常握手，以及关闭上限。普通 EOF 的原测试先通过，不把它当作已复现丢尾。
- 有真实临时 JSONL 的终端独立对话，退出后没有持久化上下文事件，新增断言先失败；修复后通过。
- 新增碎片合并和 detach 缓冲测试在旧实现上失败，改动后通过。补充固定首段计时、长度阈值与代理对边界、退出无迟到 flush。
- 空历史和损坏历史不发布“已持久化”；损坏文件仍保留；`/resume` 类历史切换不为原聊天补记上下文。保留已有配置目录隔离、审核 hook 和去重测试。

## 远端测试环境与结果

实际连接的是公网 VPS 上的 Ubuntu 24.04.4 LTS x86_64，不是 `ubuntu-cc` 业务节点。SSH 使用现有维护入口；没有重配业务隧道或替换生产容器。Node 为已有只读运行时 24.19.0；依赖、源码和测试数据放在独立 `/tmp/cc-terminal-opt-20261105-as9rZN`。

仅在一次性 Ubuntu 24.04 容器内安装编译工具，编译项目锁定的 node-pty 1.1.0，随后在 VPS Ubuntu 主机上运行真实 PTY。没有在宿主机安装全局 Node、编译器或后台服务。根测试清单只包含所需依赖；补入被桌面通道测试间接引用的发布清单和 ssh2 后完成验收。最初两轮缺少这些夹具依赖的失败保留在本机记录，未归为产品失败，也未算作全绿。

首轮最终远端测试：**137 项，126 通过，11 项 Windows 专用测试按条件跳过，0 失败**。跳过项已在本机 Windows 的同组测试中覆盖。三个改动运行文件在首次验证时的远端 SHA256 与工作区一致，摘要见 [机器可读证据](evidence/terminal-optimization-2026-11-05.json)。后续 review 修正与对应增量验收见文末。

使用 `scripts/benchmark-terminal-output.mjs` 与基线 NativeTerminal（同依赖、同机）比较，记录为单次负载测量，不据此宣称所有场景的加速比例：

| 指标 | 基线 | 修改后 |
| --- | --- | --- |
| 固定碎片写入次数 | 800 | 800 |
| 该负载发送帧数 | 800 | 40 |
| 原始输出 UTF-8 字节 | 16,200 | 16,200 |
| 服务端交付等待 P50 / P95 | 0.001 / 0.014ms | 5.299 / 6.386ms |
| 真实 Linux PTY 发送帧数 | 90 | 40 |
| 真实 PTY 输出字节 | 19,420 | 19,420 |
| 真实 PTY 800 个标记顺序与末尾标记 | 完整 | 完整 |

固定碎片负载减少 95% 帧数，真实 PTY 本次减少约 56%。这证明减少了消息和分段处理次数；不代表模型生成更快或 GPU 绘制提升同样比例。合并带来几毫秒的真实输出等待，符合设计方向，不是严格实时上限。

复现方式：在同一 Node 24 依赖环境保存基线源码到 `apps/server/src/native-terminal-baseline.ts`，执行：

```sh
node scripts/benchmark-terminal-output.mjs apps/server/src/native-terminal-baseline.ts
```

基线文件由 `git show 12ac488:apps/server/src/native-terminal.ts` 提取。脚本在 Linux 自动运行真实 PTY；Windows 会明确跳过该测量。该脚本测量传输，不是 GPU 或像素基准。

- Windows Node 24.22.1：相关核心组 136/136 通过；随后补充的计时边界及上下文负例所在组 10/10 通过。受管控制器与上下文相关组 34/34 通过。记录分次执行范围，不将重叠用例累加为唯一测试数。
- Edge 浏览器与真实 Electron：终端预测、输出、独立窗口、尺寸、ACK 等组 48/48 通过；含新增合并重绘确认与重复字符歧义测试。压缩按钮状态界面用例 1/1 通过。
- 追加性能用例 2/2 通过：同一 400 次重绘按原碎片和合并分组送入真实 xterm，最终屏幕相同，write 回调次数 400→20；接收到解析完成的 P50 为 4.9→4.6ms、P95 为 8.5→6.2ms。单次记录的 animation-frame 间隔 P95 为 13.8→7.0ms；这是测试调度间隔，不是精确像素或 GPU 耗时，不保证通用提升比例。另在模拟回声 200ms 下采集 100 次输入，预测覆盖层 DOM 插入 P95 约 0.7ms、最大约 1.4ms。原始结果纳入机器可读证据。
- 实际跨机器路径：Windows Electron 独立窗口 → 测试驱动的窄数据转发 → 本机 SSH 转发 → VPS 回环 WebSocket → 修改后的 NativeTerminal → 真实 Linux PTY。未放宽产品 CSP 或给终端子窗增加 bridge。
- 远端 PTY 使用官方 CLI 已录制启动画面和受控输入响应程序；人为增加 200ms 回显等待。`a/b/c` 各发送一次，真实回显后预测覆盖层清零并能继续输入。自动化观察到预测显示为 14/9/6ms，真实回显总等待为 379/370/367ms；这些含自动化调度与网络开销，不是精确像素延迟或 WAN RTT。不能从三个样本推导 P95。
- 此路径验证的是真实网络、PTY 和 Electron 组合，不是完整 CC Space 认证/生产执行通道或真实 Claude 模型调用；生产配置与真实账号验收仍应在后续配套发布试点执行。
- 既有中文 composition、粘贴、退格、重复字符、历史恢复、50/150/300ms 回声及迟到输出测试通过。没有进行 Windows 物理输入法、跨物理显示器或真实 GPU 驱动故障的人工验收；本轮未修改渲染器或扩大预测范围。

本机证据保存在 `.local/terminal-optimization-*`，其中含远端日志、原始 benchmark JSON、Electron 截图、控制器输出和实际测试清单。临时联调驱动为 `.local/remote-terminal-probe.mjs`、`.local/remote-terminal-browser.mjs`，不是新增产品服务。

## 用户要求的再次 review（2026-11-05）

按指定 karpathy-guidelines 复查本次差异与直接调用路径，发现并修复两项 P2 问题，均先通过新增场景复现失败：

1. **大首条 JSONL 记录仍无法启用压缩，重新打开也未使用 resume。** 持久化状态复用了只读取前 256 KiB 的标题预览；首条记录带较大附件/元数据时，预览无法解析完整行，虽然真实 SDK 已成功导入历史，仍被当作没有记录。新增 `readTerminalContext` 仅在安全打开已选历史后读取文件元数据，终端退出不再依赖标题预览；重新打开时，保留既有已识别历史行为，并对成功解析的消息提供持久化元数据补充判断。标题读取上限不放宽，不新增目录扫描。300 KB 首条记录测试同时检查持久化状态和 `--resume`；已有空/坏历史、配置目录隔离及切换原生历史测试保留。
2. **完整包获取的新错误被旧检查错误遮住。** 状态已处于 error 且保留跨协议版本时，获取完整包再次失败，弹窗优先显示此前的 `state.message`，隐藏本次原因。仅对该跨协议操作优先展示当前局部错误，保留原自动下载流程对控制器详细错误的优先级。新增测试先确认显示旧错误而失败，再验证新原因可见、按钮可重试、不会安装；普通下载错误测试继续通过。
