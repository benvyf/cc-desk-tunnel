## 发布与现有设备采用

按批准方案，先完成代码、验证和可审阅包，再确认中心发布与首台节点维护窗口。

1. 将生成的 `cc-update-service-resilient-host-updates.tar.gz` 作为新的中心运行包暂存，逐项核对 BUILD-INFO 摘要。保留现有中心目录、配置、数据与签名密钥；检查没有未完成的更新任务后切换并验证中心页面、宿主机安装器及既有发布索引。
2. 中心上线后，在 ubuntu-cc 设备面板重新生成宿主机接入命令，在该 Ubuntu 执行一次。此操作更新宿主机 agent 和基础升级脚本，不自动升级业务服务。
3. 重新接入后，现有 Build 10 基础镜像迁移即可采用新版清理、容量与备份验证脚本。保持其已签名业务归档的 Build 和摘要不变。
4. 普通更新维护入口和 supervisor 容量检查属于服务端代码，需要随下一次经过签名的服务端/基础镜像发布采用。旧 supervisor 会明确报告不支持，保留严格安装方式；不能以相同 Build 编号覆盖旧发布来启用这些功能。
5. 首台验证后，再按需安排 02、03。04、05、06 不纳入本次基础迁移。

不会自动删除镜像、容器、业务数据、账号凭据、备份或旧策略。特殊 Docker 存储文件系统及作为挂载点的业务数据根目录超出已审核的自动迁移拓扑，会在构建或切换前明确停止。
