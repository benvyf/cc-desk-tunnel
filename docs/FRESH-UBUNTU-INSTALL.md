# 新建 Ubuntu 一条命令部署

目标系统：空白 Ubuntu 24.04 LTS x64。建议 2 核、4 GB 内存，构建前至少 6 GiB 可用磁盘。Ubuntu 默认提供 Python 3；需要 sudo 权限和访问 Ubuntu 软件源、Docker Hub、nodejs.org、npm registry 及控制中心的网络。

## 使用

1. 打开控制中心“客户端更新”页的“新建 Ubuntu 一键部署”。
2. 输入唯一节点名，例如 `ubuntu-cc-2`，生成并复制命令。
3. 十分钟内在这台新 Ubuntu 的控制台执行。每台机器独立生成命令，不可把同一命令发给多台机器。下载及构建时显示进度，保持终端打开。
4. 等待 `6/6 SUCCESS`。在 Windows 客户端填写脚本显示的服务地址、证书指纹和服务凭据。再次查看：`sudo cat /var/lib/cc-fresh-install/connection.txt`。
5. 需要登录自己的 Claude 账号时，先退出所有 CC 连接，再自行执行 `sudo /usr/local/bin/cc-claude-login`，按官方 Claude Code 提示授权。程序安装不会自动登录、启动 Claude、测试会话或查询额度。

默认监听 `8787/TCP`，服务地址为 `wss://Ubuntu-IP:8787/ws`，沿用当前客户端的指纹验证方式。脚本列出 Ubuntu 本机 IPv4 地址，请使用 Windows 能访问的地址。已有的端口转发需要指向新虚拟机的 IP 和端口；脚本不修改 Windows、路由器或云防火墙的转发规则。

新节点后续按受管更新的兼容性检查确认服务端更新；首次安装命令不是日常升级入口。基础镜像迁移仅支持其各自已核实的节点范围，不能把旧节点专用迁移命令套用到新节点。

## 安装与凭据

新入口与旧节点接入完全独立。管理 API 需要现有管理员认证及同源请求；安装码用 32 字节随机数生成，服务端只保存摘要，十分钟有效，只能绑定一台安装实例。Ubuntu 在请求之前保存随机安装标识，响应丢失后可用同一标识在有效期内重新领取相同配置；另一台机器的标识无法兑换已绑定安装码。重新生成同名、尚未兑换的命令会撤销旧码；已兑换的节点禁止再次签发，避免撤销已安装节点凭据。

兑换为每个新节点生成独立监控和审核凭据，分别认证、不可互用。凭据通过安装码与随机安装标识进行用途分离的 HMAC 派生，重试返回同一凭据，服务器无需保存明文密钥。注册表在控制中心 `private/fresh-nodes.json`，只保存安装标识/凭据摘要和公开签名索引。静态节点与新注册节点在启动时合并，避免重启丢失监控记录。管理服务不修改 root 配置文件，也不为增加节点而重启。失败次数限制只拒绝错误安装码，不会阻断正确安装码。

Ubuntu 在 root 私有目录 `/var/lib/cc-fresh-install` 保存安装标识、已兑换配置、日志、经过验证的安装器和连接信息。依赖安装或构建中断后，保留该目录，使用失败提示中的本机续装命令；也可在管理页输入原节点名称，点击“生成续装命令”。续装必须在原 Ubuntu 执行，缓存中的节点和控制中心地址必须匹配；它只使用本机已领取的配置，不含安装码、不创建或轮换凭据、不修改控制中心注册表。续装命令没有领取期限，当前发布索引过期或不可用也可生成；后续仍需下载的文件及尚未完成的签名校验必须满足安装器要求。缓存缺失时会停止，不会重新兑换。静态配置节点及尚未领取配置的节点不能使用这个入口。

首次配置先在 `/srv` 下的专用临时目录生成，完成后记录阶段并原子重命名为数据目录；配置生成或发布前后中断均可重试，不会覆盖已有账号与会话。配置完成但启动/就绪检查中断时，未进入回退的重试直接使用已有镜像和凭据，不再次下载运行时、构建镜像或要求额外构建空间。已完成安装会直接显示连接信息。故障遗留的临时目录保留现场。

## 清空重装、空间检查与恢复

确需重装已有环境时，勾选“清空重装已有环境”，目标 Ubuntu 主机名必须与节点名称一致。构建前后只清理未使用的 Docker 构建缓存，分别检查安装目录、数据目录和 Docker/containerd 的实际文件系统。构建需要至少 6 GiB；冷备份和恢复还需要按当前数据逻辑大小计算额外空间，冻结原服务后再次检查，空间不足时恢复运行。

切换前要求当前容器健康、无任务且数据与配置身份未变，再为本次正在运行的环境制作完整冷备份，校验归档与源数据并记录 SHA-256。保留原容器、原镜像、原配置与独立离线回退脚本。新版必须通过 Docker 健康检查和精确版本/发布摘要的应用就绪检查，才会清理已识别的更早备份大文件及本次隔离的重复旧数据；当前所需回退归档始终保留。旧镜像、容器、正在使用的挂载、回退元数据和日志不做全局删除。清理无法验证时报告 `RETENTION_PENDING`，不把健康的新服务误报为更新失败。

重装中断后保留安装缓存和备份，使用相同节点生成续装命令；新流程会从本机日志恢复原来的重装模式。旧 v3 命令在早期失败、尚无事务记录时仍需保留“清空重装”选择。已经完成原环境回退的事务会明确阻止自动重放；先按实际回退记录核查，不会使用残留的新配置覆盖已恢复的旧数据。已兑换节点禁止新安装码签发，续装通过独立按钮进行。重装不会自动登录 Claude 账号或修改网络转发规则。

新生成的普通安装、重装和续装命令均固定安装器 SHA-256，并从 `/cc-updates/admin/fresh-install-v4.py` 下载当前安装器；该地址与规范文件 `fresh-install.py` 返回相同字节。历史 `/cc-updates/admin/fresh-install-v3.py` 保持原始字节，SHA-256 为 `fe1e387017c5a13e53797b2e0caa9cea8c9b25aa0e73c0d5cda9e37da1339b78`，避免破坏已复制命令的校验。恢复模块 `fresh-install-recovery.py` 随管理服务一同打包，由安装器固定摘要验证。

程序归档在生成命令时固定为当前签名 Linux Build。Ubuntu 使用固定公钥和 OpenSSL 3 验证 Ed25519 签名、索引有效期及归档摘要，沿用固定摘要的旧安装器中的严格 USTAR、文件清单及就绪验证函数。旧安装器主流程不执行。按签名运行时选择固定 Node 版本（当前 v3 运行时为 24.22.2），并验证 Node 与官方 Claude Code 2.1.295 下载包、原生文件摘要。重装恢复支持脚本另以固定 SHA-256 校验，未知接口版本停止切换。新镜像不调用旧 `install-linux.sh` 的 Claude 版本执行命令，签名程序文件保持原样。

构建后先使用无网络、无账号挂载及 CLI sentinel 做离线监督程序检查，随后配置 `/data` 持久化和 root 管理的 `/etc/claude-code` 只读审核挂载。正式启动只检查本机健康及受管就绪，不发送 Claude/JEV 请求。官方账号授权由用户另行发起。

## 验证范围

核心 HTTP 测试覆盖认证、安装码撤销/过期/不同机器重复领取拒绝、同机丢响应重试、独立凭据、错误码限流隔离及监控重启持久性；续装测试覆盖无发布/过期发布可生成、拒绝未注册节点、无安装码及注册文件字节不变。Linux 隔离测试使用真实 OpenSSL 签名验真与篡改拒绝，模拟 apt/Docker 的完整安装流程，检查数据拒绝覆盖、配置权限、生成/发布中断恢复、就绪失败后复用及重复执行。真实浏览器测试覆盖生成、复制、安装码过期、续装无领取期限、切换节点/退出清空及 390px 布局。HTTP 测试验证 v4 同字节别名、v3 固定摘要及恢复模块；运行包测试实际打包并验证必要资产。

这些验证不等于空白 Ubuntu VM 的完整联网安装。首次新机部署仍需在用户新建的 Ubuntu 上验收依赖下载、镜像构建、网络可达及客户端连接；不得为验收运行真实 Claude 或模型请求。
